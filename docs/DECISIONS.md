# 결정과 미결 사항

> 최종 정리: 2026-11-12. 대화에서 확인된 사용자 의도와 현재 코드의 구현 선택을 분리한다. 코드나 합의가 바뀌면 해당 항목에 날짜·근거·영향을 추가하고 관련 계약 문서도 갱신한다.

## 1. 사용자 의도로 확인된 것

| 항목 | 확인된 방향 | 아직 정해지지 않은 것 |
|---|---|---|
| 문제 | 다양한 문서의 처리와 품질을 살펴보고, 원문 위치와 버전·참조를 추적해 검색/에이전트 활용을 준비한다. 파싱 자체의 품질도 중요하다. | 고객 환경에서의 전체 범위, 검색 API의 최종 책임과 품질 목표 |
| 문서 | 원천, 파일 형식, 내용 구조는 계속 새로 생길 수 있다. 초기 목록과 분포를 지금 확정하기 어렵다. | 원천별 실제 포맷·규모·변경/삭제/권한 정보 |
| UI | 고객에게 바로 노출할 것이 확정된 화면이 아니라 내부 관리 관점의 작업 공간을 먼저 만든다. 단순한 카드 몇 개보다 탭, 사이드바, 접기·숨기기, 드래그, 형식별 흐름과 시각화가 필요하다. 시각적 완성도를 중요하게 여긴다. | 운영 담당자 범위, 배포 형태, 역할별 권한 |
| 파서와 OCR | Docling을 기반 후보로 삼고 kordoc과 OCR 전용 모델도 검토한다. 실제 문서에서 표·문자·수치와 원문 위치를 잘 처리하는지가 중요하다. | 채택할 파서·모델·버전 및 한국어/표 품질 기준. 현재 프로토타입에 OCR·kordoc이 연결된 것은 아님 |
| 분류·모델 | LLM 기반 분류는 하지 않는다. 분류가 필요해지면 판단 결과만 돌려주는 System 1 형 모델을 우선 검토한다. | 분류가 필요한 정확한 업무와 기준, 모델 선정·성능·배포/API 방식 |
| 게이트웨이 | 대상 환경에는 `base_url`, `api_key`, `model_id`로 접근하는 OpenAI 호환 게이트웨이가 있다. 앱은 `.env` 설정으로 연결 확인·모델 목록 조회만 한다. | 사용 가능한 실제 모델 목록, 모델별 API 호환성, 추가/등록 권한·보안·성능·호출 비용. 문서 처리 단계에는 아직 연동하지 않음 |
| 문서 계보·참조 | 이전 경험에서 문서 안에 문서가 숨어 있거나 링크로 다른 문서를 가리켜 대상이 계속 늘어나는 문제가 확인됐다. 추측 대신 실제 파일 구조를 열어 하위 문서·링크·암호화를 보여 주는 분석기를 둔다. | 실제 데이터의 확장 배율·깊이·링크 분포, 링크 대상과의 실제 매칭 규칙 |
| 품질 측정 | 파서 성능 측정 틀은 필요하다. 골드셋 버전 관리 기능은 만들지 않는다. | 측정 지표와 형식별 기준, 측정용 표본 |
| 협업 | 구현 도중 독립적인 UI/UX 검토와 병렬 작업을 허용한다. | 작업별 분담은 실제 환경과 작업 범위에 따라 정한다. |

## 2. 현재 프로토타입의 구현 선택

이는 현재 코드가 택한 방식이며, 고객 운영 환경의 확정 설계는 아니다.

1. **Mock 우선 + 별도 실제 처리:** Mock 대시보드와 파이프라인 화면을 유지하면서 별도의 실제 로컬 파일 처리 화면을 추가했다. 두 목록/수치는 동기화되지 않는다.
2. **하나의 프로젝트 디렉터리:** `frontend/`와 `backend/`를 한 저장소(`unstructured-parser-control-plane`)에 둔다. 화면 이름은 "비정형 리뷰 (Unstructured Review)"다. 브라우저 저장 키(`document-ops:*`)와 환경변수 접두사(`DOCOPS_*`)는 기존 설정 호환을 위해 이전 이름을 유지한다.
3. **작은 로컬 백엔드:** FastAPI, SQLite, 원본·결과 파일, 단일 워커와 메모리 대기열을 사용한다. 운영 환경의 큐, 데이터베이스, 분산 배포, 인증 구조는 결정하지 않았다.
4. **파서 경계:** TXT·CSV·MD·LOG는 경량 파서, PDF·DOCX·PPTX·XLSX는 선택적 Docling 어댑터로 연결한다. 합성 DOCX·텍스트 PDF는 실제로 시험했고 PPTX·XLSX의 결과 품질은 미검증이다. 실제 지원 여부는 코드와 테스트를 함께 확인한다.
5. **오류의 가시성:** 신규/미지원 형식은 억지로 성공시키지 않고 상태를 표시한다. 재처리 중·실패 후에는 이전 성공 결과를 보존하고 `is_stale`로 구분한다. OCR이 꺼진 PDF 결과는 스캔 누락 가능성을 경고한다.
6. **브라우저 내 설정:** 위젯과 파이프라인 미리보기의 배치·표시 설정은 `localStorage`를 사용한다. 실제 운영 정책, 공유 설정, 감사 이력으로 사용하지 않는다.

## 3. 이후 결정할 항목

| 결정 주제 | 현재 상태 | 결정을 위한 근거 |
|---|---|---|
| 실제 대시보드 연계 | Mock과 실제 처리 목록 분리 | 실제 운영자가 보는 범위, 상태·시간의 의미, 소스 및 권한, 샘플 처리 이력 |
| 실제 파이프라인 구성 | UI 편집은 예시만 변경 | 파서 계약·입출력, 분기 조건, 실패 처리, 구성 버전·적용/롤백 방식 |
| 스캔 OCR | 미구현 | 합성 및 사용 허가된 실제 표본의 한글·숫자·단위·표 정확도, 모델 자원·오프라인 배포 가능성 |
| XLSX·문서 참조 | 구조 분석에서 셀 단위 하이퍼링크·외부 통합문서 참조·문서번호 후보 추출. 대상 문서 매칭과 관계도 연결은 미구현 | 시트·셀·수식·하이퍼링크 예시, 문서번호·버전 규칙, 연결 불확실성 처리 |
| 분류와 빠른 판단 모델 | 미구현 | 분류가 필요한 구체적 사용처, 규칙 기준선과 한국어 평가셋, 지연·정확도·라이선스 |
| 게이트웨이 연결 | `.env` 설정으로 연결 확인·모델 목록 조회만 구현 | 실제 권한·지원 프로토콜, 비밀 관리 방식, 데이터 반출 범위, 모델별 연결 테스트 |
| 검색·에이전트 인터페이스 | 미구현 | 검색 사용 시나리오, 원문 근거·버전·권한 반환 계약, 변경·삭제 반영 정책과 평가 기준 |
| 운영 전환 | 단일 사용자 로컬 프로토타입 | 인증·인가, 저장/보존/삭제, 감사, 복구, 운영형 작업 큐, 부하와 배포 환경 |
| GitHub | 공개 저장소 `unstructured-parser-control-plane`에 게시. 고객 데이터가 들어가면 저장소 분리 검토 | 고객 데이터 반입 시점과 분리 범위 |

새 결정을 문서화할 때는 **날짜 / 결정 / 근거 / 영향 / 남은 위험 / 관련 코드·문서**를 포함한다. 구현 예정이나 개인 제안을 확정 결정으로 승격하지 않는다.
