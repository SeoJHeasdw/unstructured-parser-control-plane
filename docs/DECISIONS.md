# 결정과 미결 사항

> 최종 정리: 2026-11-12. 2026-11-19에 §4(watsonx.data 연계안, 제안)를 추가했다. 대화에서 확인된 사용자 의도와 현재 코드의 구현 선택을 분리한다. 코드나 합의가 바뀌면 해당 항목에 날짜·근거·영향을 추가하고 관련 계약 문서도 갱신한다.

## 1. 사용자 의도로 확인된 것

| 항목 | 확인된 방향 | 아직 정해지지 않은 것 |
|---|---|---|
| 문제 | 다양한 문서의 처리와 품질을 살펴보고, 원문 위치와 버전·참조를 추적해 검색/에이전트 활용을 준비한다. 파싱 자체의 품질도 중요하다. | 고객 환경에서의 전체 범위, 검색 API의 최종 책임과 품질 목표 |
| 문서 | 원천, 파일 형식, 내용 구조는 계속 새로 생길 수 있다. 초기 목록과 분포를 지금 확정하기 어렵다. | 원천별 실제 포맷·규모·변경/삭제/권한 정보 |

| 게이트웨이 | 대상 환경에는 `base_url`, `api_key`, `model_id`로 접근하는 OpenAI 호환 게이트웨이가 있다. 앱은 `.env` 설정으로 연결 확인·모델 목록 조회만 한다. | 사용 가능한 실제 모델 목록, 모델별 API 호환성, 추가/등록 권한·보안·성능·호출 비용. 문서 처리 단계에는 아직 연동하지 않음 |
| 문서 계보·참조 | 이전 경험에서 문서 안에 문서가 숨어 있거나 링크로 다른 문서를 가리켜 대상이 계속 늘어나는 문제가 확인됐다. 추측 대신 실제 파일 구조를 열어 하위 문서·링크·암호화를 보여 주는 분석기를 둔다. | 실제 데이터의 확장 배율·깊이·링크 분포, 링크 대상과의 실제 매칭 규칙 |
| 품질 측정 | 파서 성능 측정 틀은 필요하다. 골드셋 버전 관리 기능은 만들지 않는다. | 측정 지표와 형식별 기준, 측정용 표본 |
| 협업 | 구현 도중 독립적인 UI/UX 검토와 병렬 작업을 허용한다. | 작업별 분담은 실제 환경과 작업 범위에 따라 정한다. |
| 벡터 DB (2026-11-17) | Milvus를 쓴다. 콘솔에서 컬렉션·파티션 구성과 저장된 청크를 사람이 읽을 수 있는 텍스트로 확인한다. 벡터 차원은 컬렉션마다 고정이라 모델·차원을 바꾸면 새 컬렉션과 전체 재임베딩이 필요하다. | 사용할 Milvus 버전과 접속 방식(REST 허용 여부), 컬렉션·파티션 설계, 스칼라 필드(문서 ID·버전·보안등급·원문 위치) |
| 임베딩 모델 (2026-11-17) | 아직 정하지 않았다. 최소 검토 후보는 Harrier-OSS-v1 0.6B(1024차원, 최대 32K 토큰)다. slate·granite 임베딩은 최대 입력 512토큰과 작은 차원 때문에 사용 의무가 없으면 제외하는 방향이다. 질의 측과 문서 측은 같은 모델·버전을 쓴다. | 대상 환경에서 쓸 수 있는 모델, 한국어 평가 결과, 처리량과 자원 |
| 검색 범위 (2026-11-17, 구상) | 우리 범위는 search 엔드포인트가 받은 질의에 가장 정확한 근거를 돌려주는 것까지다. 질의 재작성, 하위 질문 분해, 재검색 판단은 에이전트 개발 측이 맡는다. 구상은 하이브리드 검색(dense + sparse) + 리랭커다. | 에이전트 측과의 API 계약, 묶음 요청 여부, 권한 전달 형식, 응답 시간 목표, 리랭커 모델 |
| 문서 계보 (2026-11-17) | 문서 관계 화면은 계층 구조로 본다: 어떤 파일이 최신인지, 무엇을 담고 있는지(압축·첨부·내장 개체), 무엇을 가리키고 무엇이 가리키는지. | 실제 파일명·문서번호 버전 규칙, 최신 판단 기준, 링크 대상 매칭 규칙 |
| 작업 에이전트 도구 (2026-11-24) | 사용자 확인: 사용자는 구축팀 2명, 고객사 PC의 OpenCode Desktop + 사내 중형 모델(선택권 없음, 불안정 가정), 에이전트는 실험·보고만 하고 코드를 고치지 않음, 고객사 PC 파일은 반출 불가라 사람이 보고서를 옮겨 적음, WSL 막힘·Git Bash에서 `run.sh` 사용, 고객사에 Milvus 없음. 범위·승인 정책은 사용자가 설계를 위임했다. 정한 선택: 파싱·검수 → 청킹·평가 → Milvus 적재 → 검색 4단계(1단계 구현), 조회·로컬 처리는 자동, 50개 넘는 묶음은 미리보기 후 진행, Milvus 쓰기는 계획→실행 분리 후 실행만 승인(미구현), 삭제·서버 재시작·설정 변경 도구는 만들지 않음. | 고객사 OpenCode Desktop 버전과 설정 형식, 게이트웨이 중형 모델의 실제 도구 호출 안정성, 2~4단계 도구 계약 |


### OCR은 모델만 (2026-11-24, 사용자 결정)

| 항목 | 내용 |
|---|---|
| 결정 | OCR은 문서 OCR 모델만 쓴다. EasyOCR·Tesseract 같은 라이브러리 OCR은 사용·벤치마크 모두 하지 않는다. |
| 근거 | 사용자 경험상 라이브러리 OCR 품질이 매우 낮다. 실측: EasyOCR 스캔 COA 숫자+단위 26개 중 11개 적중인데 결과는 `ok`. |
| 영향 | EasyOCR 경로를 껐다. OCR 모델은 고객사 게이트웨이에 서빙을 요청할 예정이라 OpenAI 호환 비전 API로 연결한다. 후보: GLM-OCR, PaddleOCR-VL-1.6, Schift schift-ocr-1-beta(한국어 특화) 등. |
| 남은 위험 | 게이트웨이에 OCR 모델이 언제 올라갈지 미정. 그 전까지 스캔·이미지 글자는 추출되지 않는다. 후보 모델의 한국어·표·숫자 품질은 이 Mac 시험과 고객 문서로 확인해야 한다. |

### 설치·실행: `setup` / `run`, 기본은 전체, 가벼운 설치는 `--lite` (2026-11-25, 사용자 결정)

| 항목 | 내용 |
|---|---|
| 결정 | 설치(`setup.cmd`·`setup.sh`)와 실행(`run.cmd`·`run.sh`)을 나눈다. 진입점은 Python만 찾는 얇은 래퍼이고, 로직은 `scripts/console.py` 하나에 둔다. setup의 기본 모드에 Docling(PDF·Office 파싱)과 PDF 모델 받기를 포함하고, Docling 없이 설치할 때는 `--lite`를 쓴다. 가상환경은 `backend/.venv` 하나다. run은 설치하거나 네트워크를 쓰지 않는다. |
| 근거 | 사용자는 구축팀 2명(사용자와 부장님)이고, 시험 단계라 PDF·Office를 포함한 모든 제약을 봐야 한다. `--docling`을 매번 붙이고 가상환경을 둘로 나누는 방식은 헷갈리고, "사용자는 setup·run만 알면 된다"는 사용자 의견이다. Windows용(Python)과 bash용 설치 로직이 이중으로 있어 고칠 때마다 두 곳을 맞춰야 했다. 고객사 PC는 PyPI·npm 접속이 열려 있다(사용자 확인). |
| 영향 | 기본 setup은 Python 3.12가 필요하고, 첫 설치에 Docling(torch 포함)이 들어가 시간이 걸린다. 코드를 업데이트한 뒤에는 setup을 다시 실행해야 하며, run이 이를 알려 준다. 사용자가 혼자 쓰는 단계라 `start.cmd`와 호환용 옵션(`--base`·`--docling`·`--check`)을 없앴다(사용자 결정). 예전 `backend/.venv-docling`은 쓰지 않으며, 실행기가 지우지는 않는다. 오프라인 기본 묶음(Docling 휠 없음)은 `setup.cmd --offline --lite`로 설치한다. |
| 남은 위험 | Windows 실기기에서 새 진입점과 전체 모드 첫 설치를 돌려보지 않았다. 고객사에서 `huggingface.co`가 막혀 있으면 PDF 모델은 따로 옮겨야 한다(2026-11-25 막힌 것을 확인, 아래 항목). 이때 setup은 계속하되, 맨 끝 요약과 run 시작 화면에 남긴다. CI(`windows.yml`)는 시간 때문에 `--lite`로 점검한다. |

### huggingface.co 차단 확인 → PDF 모델은 ZIP으로 옮긴다 (2026-11-25)

| 항목 | 내용 |
|---|---|
| 사실(사용자 확인) | 고객사 PC에서 `huggingface.co` 접속이 막혀 있다. PyPI·npm은 열려 있다(11-25 앞선 확인). |
| 구현 선택 | setup은 받기 전에 `huggingface.co`(또는 `HF_ENDPOINT`)에 10초 안에 접속되는지 확인하고, 막혀 있으면 `docling-tools`를 부르지 않고 원인(403·407·시간 초과·인증서 등)을 한 줄로 알린다. 접속되는 PC에서 `prepare-offline.py --models-only`로 모델만 묶은 ZIP(파일별 크기·SHA-256 `manifest.json`)을 만들고, 막힌 PC에서 `setup --models <ZIP|폴더>`로 검증해 콘솔이 모델을 찾는 폴더에 설치한다. 다른 내용의 기존 모델 파일은 덮어쓰지 않고 멈춘다(사용자 데이터·모델 캐시를 지우지 않는 원칙). 사내 HF 미러가 있으면 `HF_ENDPOINT`로 받을 수 있게 안내만 했다. |
| 근거 | 막힌 망에서 `docling-tools`는 긴 Python 오류 추적을 쏟고 실패했다(이 저장소의 클라우드 개발 환경도 `huggingface.co`가 막혀 같은 현상을 재현). 고객사 PC로 파일을 반입하는 경로는 이미 소스 ZIP으로 쓰고 있다. |
| 영향 | 모델 ZIP을 만들 PC(사용자 Mac 등)와 반입 절차가 필요하다. 모델 묶음은 약 수백 MB로 예상한다(실제 크기는 만들 때 표시). 모델 가중치는 소스 저장소에 넣지 않는다. |
| 남은 위험 | 실제 모델 파일로 묶기·설치를 돌려보지 않았다(이 개발 환경도 HF가 막혀 가짜 파일로만 확인). 고객사에 HF 미러가 있는지, ZIP 반입이 보안 정책상 허용되는지 확인하지 않았다. |

### PDF 모델 설치 보류 (2026-11-25, 사용자 결정)

| 항목 | 내용 |
|---|---|
| 결정 | 고객사 PC에 Docling PDF 모델(레이아웃·표)을 넣는 일은 보류한다. |
| 근거(사용자 확인) | 고객사 PC 사양이 Intel i5 10세대 · RAM 16GB다. 이 PC에서 레이아웃·표 모델을 CPU로 돌리는 것은 처음부터 맞지 않다고 판단했다. |
| 영향 | 고객사 PC에서는 PDF 파싱이 `parser_unavailable`(PDF 모델 없음)로 실패한다. DOCX·PPTX·XLSX·XLSM·텍스트·CSV는 모델 없이 된다. 모델 ZIP 설치(`setup --models`)와 접속 사전 확인은 만들어 둔 채로 두며 쓰지 않는다. OCR은 원래 게이트웨이 모델이라 이 PC 사양과 무관하다. |
| 남은 위험 | 고객사 PDF를 어디서(게이트웨이·서버·다른 PC) 어떤 방식으로 파싱할지 정하지 않았다. PDF 처리 시간·자원은 고객사 사양으로 재 보지 않았다. |

### PDF 모델이 없을 때 글자 층 파서로 읽기 (2026-11-25, 사용자 요청 '파서 개선점 선제 개선' → 구현 선택)

| 항목 | 내용 |
|---|---|
| 구현 선택 | 레이아웃·표 모델 파일이 없으면 PDF를 실패(`parser_unavailable`)로 두지 않고 `pdf-text`(pypdfium2 글자 층, 모델 없음)로 읽는다. 모델이 갖춰지면 자동으로 Docling 경로로 돌아간다. 파서 이름·버전(`pdf-text`, `pypdfium2 x`)과 한계 경고를 항상 남겨 Docling 결과와 섞이지 않게 한다. |
| 근거 | PDF 모델 보류(위 항목)로 고객사 PC에서 PDF가 전부 실패한다. pypdfium2는 Docling과 함께 이미 설치되어 새 의존성이 없다. 합성 말뭉치 디지털 PDF 7건에서 정답 숫자+단위 63/63, 문장 조각은 그림 속 글자 4개를 빼고 모두 찾았고, 120쪽 문서도 0.3초에 끝났다(이 개발 환경). |
| 영향 | PDF 표는 칸 구조 없이 줄 글자로 나와 표 셀 비교·청킹의 표 인식은 약해진다. 여러 단·글상자 쪽은 읽는 순서가 섞일 수 있다. 큰 그림·깨진 글자 층·빈 쪽은 쪽 번호와 함께 경고한다. |
| 남은 위험 | 실제 고객 PDF(다단·복잡한 표·회전 쪽·특수 글꼴)로 확인하지 않았다. 회전한 쪽의 큰 그림은 잘라 읽지 않는다. |

### 추출 결과 읽기 보기와 원문 대조의 Office 원본 그리기 (2026-11-25, 사용자 요청 → 구현 선택)

| 항목 | 내용 |

| 구현 선택 | DOCM은 DOCX 경로에 내용 형식만 DOCX로 바꾼 메모리 사본을 넘긴다(매크로 경고는 `vba.py`). HTM·MHT는 인코딩을 우리가 정해(BOM·MIME charset·meta·UTF-8·CP949 추정, 근거를 `evidence`에) Docling `convert_string`으로 넘기고, 첫 제목 앞 글·`<footer>`를 남기고 `<title>`은 뺀다. 외부·로컬 자원은 열지 않는다. MSG는 기존 CFB 읽기 위에 [MS-OXMSG] 속성 읽기(`app/msg.py`)를 두고 EML과 같은 결과 모양으로. 원본 읽기: HTML은 표준 라이브러리 해석(파서와 별개), MSG는 같은 속성 스트림(`same_layer`, 비차단). |
| 택하지 않은 것 | LibreOffice 변환(사용자 의견: 파이썬으로 배포할 파서에 외부 프로그램 설치가 맞지 않음, 배포·보안 승인 부담). Docling의 MHTML 경로(인코딩 판정과 근거를 우리가 남기려고 대표 HTML을 직접 꺼냄). `extract-msg` 같은 새 의존성(CFB 읽기가 이미 있음). 압축 RTF 본문 지원(이번 범위 밖, 경고와 `source_unread`로 드러냄). |
| 영향 | 경로가 없는 것은 DOC·XLS·PPT·ZIP 넷. 새 경고 코드 `macro`·`attach-list`·`mail-deep`·`rtf-skip`·`no-body`·`signed`·`enc-guess`·`enc-mis`(EML 경고도 이제 `other`가 아님). 자동 대조에 `source_unread`(원본에 있지만 읽지 못한 부분, 차단) 근거가 생겼다. DB 변경 없음. |
| 남은 위험 | 모두 합성 파일로만 확인했다: Outlook이 저장한 실제 MSG(받는 사람 저장소 없는 경우, 8비트 문자열, RTF 본문 비율), Word·IE가 저장한 실제 HTM·MHT(조건부 주석·VML·여러 HTML 부분), Excel·Word가 저장한 실제 DOCM. Docling HTML 처리기가 `aria-hidden` 글을 빼는 점은 원본 읽기가 '빠짐'으로 잡는다(화면에는 보이는 글). 스타일시트에서 숨긴 요소는 원본 읽기도 보지 않는다. |

## 2. 현재 프로토타입의 구현 선택

이는 현재 코드가 택한 방식이며, 고객 운영 환경의 확정 설계는 아니다.

1. **Mock 우선 + 별도 실제 처리:** Mock 대시보드와 파이프라인 화면을 유지하면서 별도의 실제 로컬 파일 처리 화면을 추가했다. 두 목록/수치는 동기화되지 않는다.
2. **하나의 프로젝트 디렉터리:** `frontend/`와 `backend/`를 한 저장소(`unstructured-parser-control-plane`)에 둔다. 화면 이름은 "비정형 관리 콘솔 (Unstructured Data Console)"이다(2026-11-17, "비정형 리뷰"에서 변경). 브라우저 저장 키(`document-ops:*`)와 환경변수 접두사(`DOCOPS_*`)는 기존 설정 호환을 위해 이전 이름을 유지한다.
3. **작은 로컬 백엔드:** FastAPI, SQLite, 원본·결과 파일, 단일 워커와 메모리 대기열을 사용한다. 운영 환경의 큐, 데이터베이스, 분산 배포, 인증 구조는 결정하지 않았다.
4. **파서 경계:** TXT·CSV·MD·LOG는 경량 파서, PDF·DOCX·PPTX·XLSX·XLSM은 선택적 Docling 어댑터로 연결한다(XLSM은 2026-11-25부터, 매크로 미실행). 합성 DOCX·텍스트 PDF는 실제로 시험했고 PPTX·XLSX의 결과 품질은 미검증이다. 실제 지원 여부는 코드와 테스트를 함께 확인한다.
5. **오류의 가시성:** 신규/미지원 형식은 억지로 성공시키지 않고 상태를 표시한다. 재처리 중·실패 후에는 이전 성공 결과를 보존하고 `is_stale`로 구분한다. OCR이 꺼진 PDF 결과는 스캔 누락 가능성을 경고한다.
6. **브라우저 내 설정:** 위젯과 파이프라인 미리보기의 배치·표시 설정은 `localStorage`를 사용한다. 실제 운영 정책, 공유 설정, 감사 이력으로 사용하지 않는다.

| 항목 | 내용 |
|---|---|
| 날짜 | 2026-11-19 |
