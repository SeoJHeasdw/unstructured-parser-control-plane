01결정 요청

이번 회의에서 여섯 가지를 정한다

세 가지 원칙을 전제로 한다. 항목마다 결정 시점과 근거 장을 함께 적었다.

원칙 1

제품 우선

제품에 있는 기능은 별도로 만들지 않는다. 벡터 저장·검색은 watsonx.data Milvus를 쓰고, 배포·운영과 데이터 형상은 제품 체계를 따른다.

원칙 2

접점 최소화

제품과는 표준 인터페이스로만 연결한다. Milvus 접속, OpenAI 호환 임베딩 호출, 파서 공통 결과 형식. 제품 일정이나 사양이 바뀌어도 설정 변경으로 대응한다.

원칙 3

평가 기반 결정

기술 선택과 오픈 판단은 같은 평가셋의 점수로 한다. 제품 기능이 기준을 넘으면 해당 영역은 제품으로 전환한다.

04평가 계획

평가셋을 고정하고 매주 한 가지씩 바꿔 측정한다

점수가 떨어진 회차도 원인을 기록하면 진행으로 본다. 측정 도구는 운영 콘솔에 이미 갖춰져 있다.

대상지표의미측정 도구오픈 기준
파싱정답 자료 대조원문 표의 숫자·단위·문서번호가 결과에 그대로 남았는가콘솔 파싱 비교합의 필요

검색MRR@10정답이 몇 번째에 나오는지. 첫 번째면 1, 두 번째면 0.5콘솔 임베딩 평가합의 필요
근거원문 위치 일치율돌려준 근거의 페이지·시트·셀이 맞는 비율검색 API 평가구현 예정합의 필요

평가셋은 업무 담당자가 실제로 묻는 질문과 그 정답 문서로 만든다. 문서 형식(PDF·XLSX·HWP 등)과 업무별로 고르게 담고, 회차가 지날수록 어려운 질문을 보탠다. 첫 평가셋은 12월 첫 회차 전에 필요하다.

측정 도구: 운영 콘솔

콘솔 화면의 일부다. 화면 속 문서와 수치는 모두 예시 데이터이고, 실제 문서를 넣으면 같은 화면으로 회차를 측정한다. 화면을 누르면 크게 볼 수 있다.

임베딩 서빙

판단 G1 · 12월 말

Qwen3-Embedding-4B를 제품(watsonx.ai)에서 서빙할 수 있나?

  • 확인됨Qwen3-Embedding-4B는 2560차원, 최대 32K 토큰 입력. 출력 차원을 32~2560 사이로 줄일 수 있다(MRL).
  • 확인됨watsonx.ai는 Cloud Pak for Data 5.0부터 커스텀 파운데이션 모델 배포를 지원한다.
  • 확인 필요커스텀 배포가 임베딩 모델 구조를 받는지, GPU 요건(커뮤니티 자료상 A100·H100 80GB급), 임베딩 API 형식.

A지원되면

제품 서빙을 쓴다. 교체 지점 ②에서 주소와 어댑터만 바꾼다. 제품 API 형식이 OpenAI 호환과 다르면 어댑터를 하나 추가한다.

B지원되지 않으면, 순서대로

  1. 고객사 사내 게이트웨이에 등록한다. 이미 여러 모델을 서빙하고 있어 가장 빠르다.
  2. 처리량이나 지연이 기준에 못 미치면 등록 조건 변경을 요청하거나 직접 서빙한다(GPU 확보 시, D5).
  3. 모두 어려우면 경량 모델(Harrier-OSS-v1 0.6B, 1024차원)로 낮추고 성능 차이를 평가 결과로 보고한다.
준비 기준OpenAI 호환 /embeddings 경계로 개발하고 게이트웨이 등록을 먼저 요청한다. 제품 확인은 병행한다.

공통 질의와 문서는 같은 모델·버전·차원을 쓴다. 모델이나 차원이 바뀌면 컬렉션을 새로 만들고 전체를 재임베딩한다(03). 모델 후보는 4회차 평가로 비교한다.

D2

하이브리드 검색

입고 전 IBM 확인 · 입고 직후 실측

watsonx.data에 포함된 Milvus가 BM25 전문 검색을 내장한 버전(2.5 이상)이고, 한국어 분석기를 쓸 수 있나?

  • 확인됨Milvus는 2.5(2024년 12월)부터 Sparse-BM25 전문 검색을 내장했다.
  • 확인 필요입고될 watsonx.data의 Milvus 버전과 한국어 토크나이저 지원. 공개 자료로는 확인하지 못했다.
  • 제공기존 RAG는 BM25 0.3 + 벡터 0.7 가중 하이브리드를 쓴다.

A내장돼 있으면

Milvus 안에서 BM25와 dense 검색을 함께 실행한다. 기존 가중치 0.3/0.7을 출발점으로 다시 측정한다.

B없으면

  • 2.4 이상이면 BM25 sparse 벡터를 자체 생성(한국어 형태소 분석 포함)해 Milvus sparse 필드에 넣는다.
  • 그보다 낮으면 키워드 색인을 별도로 두고 검색 API에서 두 결과를 합친다.
준비 기준sparse 벡터를 직접 만드는 쪽으로 개발한다. 버전과 무관하게 동작하고, A가 확인되면 생성 단계만 제거한다.
D3

제품 입고 시점

판단 G2 · 1월 말

1월 안에 제품이 설치되어 사용할 수 있나?

  • 제공입고는 1월 이후이며 더 늦어질 수 있다. 운영 오픈은 3월이다.
  • 계산2월 1일 입고가 제품 위 시험 4주를 남기는 마지막 날이다(02 그림).

A1월에 입고되면

1월에 설치하고 접속·권한을 확인하며 이관을 리허설한다. 2월에 통합·부하 테스트와 전체 적재를 하고, 3월에 제품 위에서 오픈한다.

B2월 이후면

제품과 같은 버전의 자체 Milvus로 스테이징까지 완성해 둔다. 오픈 방식은 PMO가 정한다.

  • (가) 임시 운영 후 이관. 3월에 자체 Milvus로 열고, 제품이 들어오면 청크 정본에서 다시 적재해 전환한다. 검색 API 주소는 그대로라 에이전트 쪽 변경은 없다. 상단 구조도의 ‘Milvus 입고 전/후’가 이 전환이다.
  • (나) 오픈 연기. 제품 입고 후 통합 테스트를 마칠 때까지 오픈을 미룬다.
준비 기준A 일정으로 진행한다. (가)와 (나) 중 선택은 G2 전에 PMO와 합의해 둔다.

사전 합의가 필요한 이유 입고 지연은 통제할 수 없는 변수다. 선택지를 미리 정해 두지 않으면 2월에 일정 협의가 다시 필요해진다.

D4

파싱 경로

입고 후 형식별 판정

UDI가 해당 형식을 자체 기준 이상으로 처리하나?

  • 확인됨IBM 자료는 70종 이상의 형식을 지원한다고 소개한다. 버전별 실제 목록은 해당 버전 문서로 확인해야 한다.
  • 제공현장 검토 결과 지원하지 않는 확장자가 많고, 문서 속 문서·링크 참조 같은 경우를 다루지 못한다(02 문서 계보 화면).

A기준을 넘으면

해당 형식은 UDI로 보낸다(교체 지점 ①). 결과를 공통 형식으로 받아 청킹부터는 같은 경로를 탄다.

B기준에 못 미치면

자체 파서(Docling과 형식별 전용 어댑터)로 처리한다. 고객사 기존 파서 소스도 후보로 함께 비교한다.

준비 기준자체 파서로 개발한다. 입고 후 같은 표본을 UDI로 처리해 9회차에 형식별로 판정한다.

판단 기준 같은 표본에서 본문, 표, 숫자·단위, 원문 위치가 얼마나 일치하는가. 콘솔의 파싱 비교 화면(04)으로 측정한다.

D5

GPU

판단 G1 · 12월 말

사용 가능한 GPU가 있나?

  • 확인 필요현재 미정. 종류·수량·사용 가능 시점을 모른다.

A있으면

리랭커와 OCR을 직접 서빙한다. 필요하면 임베딩도 직접 서빙한다(D1 B-2).

B없으면

임베딩과 리랭커는 게이트웨이를 거친다. OCR은 텍스트 PDF부터 처리하고, 스캔 문서는 범위를 줄이거나 CPU 경량 후보를 시험한다. 현재 콘솔도 OCR은 꺼져 있고 PDF 결과에 누락 가능성 경고를 붙인다.

준비 기준GPU 없이 동작하는 구성으로 개발한다. GPU가 확보되면 서빙 위치만 옮긴다.
D6

Milvus 운영 권한

입고 시

자체 서비스가 watsonx.data Milvus에 컬렉션을 직접 만들고 인덱스를 바꿀 수 있나? 접속 방식과 인증은?

  • 확인 필요접속 방식(gRPC·REST), 인증, 외부 서비스에 주는 권한 범위.

A권한이 있으면

파이프라인이 컬렉션·파티션·인덱스를 직접 관리하고, 스키마는 코드와 함께 버전 관리한다.

B제품이 관리하면

제품 관리 체계에서 컬렉션을 만들고 자체 서비스는 적재와 조회만 한다. 스키마는 선언 파일로 넘겨 등록을 요청한다.

준비 기준스키마를 선언 파일로 관리한다. 어느 쪽이든 그대로 쓸 수 있고, 제품의 형상 체계를 따르는 방식이다.

평가와의 관계 회차마다 컬렉션을 새로 만들 수 있어야 재구축이 빠르다. B라면 평가용 컬렉션 생성 권한을 별도로 요청한다.

D7

기존 RAG 승계

판단 G1 · 12월 말

기존 시스템의 임베딩 모델과 인덱스를 이어받을까, 새 모델로 다시 만들까?

  • 제공에이전트 4개, MCP 도구 6개, 4096차원 벡터, BM25 0.3 + 벡터 0.7 하이브리드. 파서·임베딩 소스 확보.
  • 확인 필요4096차원 모델의 정체. Qwen3-Embedding-8B가 4096차원이다(4B는 2560차원). 받은 소스에서 모델명을 확인한다.

A승계하면

기존 벡터를 재임베딩 없이 옮길 수 있는지(저장소 형식, 메타 필드) 확인한다. 벡터 용량은 아래 그림에서 가장 크다.

B새로 구축하면

Qwen3-Embedding-4B(또는 D1 결과)로 전체를 재임베딩한다. 1회차 기준선과 4회차 후보 비교로 이점을 확인하고 결정한다.

청크 100만 개당 원시 벡터 용량

계산

float32 기준. 인덱스와 복제본은 별도다. 청크 100만 개는 계산용 예시이고 실제 물량은 미확인이다.

준비 기준1회차에 기존 시스템을 기준선으로 측정한다. 모델 결정은 G1에서 D1과 함께 한다.

공통 기존 MCP 도구 6개는 참고만 하고 명세는 맞추지 않는다. 정형 데이터 도구(query_edw, edw_meta)는 이 설계 범위 밖이다.
