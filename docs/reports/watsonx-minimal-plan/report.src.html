점수가 정체될 때

점수가 일정 수준에서 멈추는 구간은 거의 반드시 온다. 오답에는 파싱·청킹·임베딩·검색 순위 문제가 섞여 있어 전체 점수만으로는 무엇을 바꿔야 할지 보이지 않는다. 그래서 처음부터 단계별로 따로 재고, 오답을 유형별로 나눠 원인 단계를 좁힌 뒤, 재구축 비용이 낮은 시도부터 빨리·많이 돌린다.

오답 유형확인 방법의심 단계먼저 시도할 것재구축
정답 문서가 상위 10개에도 없음Hit@10청킹·임베딩·키워드청킹 단위, 임베딩 후보·차원, BM25 가중치2~4단계
정답 문서는 있으나 순위가 낮음Hit@10은 맞고 Hit@1·MRR이 낮음순위하이브리드 가중치, 리랭커재평가만
문서는 맞는데 근거 구절이 틀림정답 구절 기준 채점청킹부모-자식, 표 통째 청킹4단계
표의 숫자·단위가 틀림파싱 정답 자료 대조파싱형식별 파서 교체, 표 구조 보존5단계
질문이 모호하거나 범위 밖질문 유형 분류평가셋·질의질문 정제, 에이전트 측 질의 재작성없음

콘솔 임베딩 평가는 Hit@1·3·5·10과 MRR을 정답 문서·정답 구절 기준으로 나눠 채점하고, 파싱 비교는 정답 자료와 대조한다. 재구축 단계 수는 위 ‘변경 범위별 재구축 단계’ 기준이다. 정체 구간을 3월 전에 지나가려면 제품을 기다리지 않고 12월부터 시도를 쌓아야 한다.

설계 목표: 재구축 비용 최소화

청크 정본이 있으면 임베딩·Milvus·검색 쪽 변경은 재파싱 없이 시작한다. 교체 지점(05)은 제품 전환을 설정 변경으로 만들고, 자동 재평가는 회차마다 같은 기준을 보장한다. 재구축 시간이 짧아야 18주 안에 17회 평가할 수 있다.

06차원과 메모리

벡터 차원이 메모리와 서빙 자원을 결정한다

차원은 Milvus 메모리, 검색 연산량, 임베딩 모델 서빙 자원을 함께 정한다. 기존 시스템의 4096차원을 그대로 받으면 세 가지가 모두 가장 크다. 차원은 평가로 정하고(D7), 아래 수치는 청크 100만 개 기준 계산값이다.

차원이 바꾸는 세 가지

  1. 1Milvus 메모리. 차원이 4배면 벡터 메모리도 4배다. 4096차원은 100만 개당 15.3 GiB, 1024차원은 3.8 GiB.
  2. 2검색 연산량. 거리 계산량이 차원에 비례한다. 4096차원은 1024차원의 4배, 2560차원은 2.5배다.
  3. 3모델 서빙 자원. 차원이 큰 모델일수록 모델 자체도 크다. 가중치만으로 8B급은 약 16GB, 4B급은 약 8GB다(아래 표).
모델을 바꾸지 않고 차원만 낮추는 선택지

Qwen3 임베딩은 MRL을 지원해 같은 모델에서 출력 차원을 줄일 수 있다(4B는 32~2560, 8B는 32~4096). 기존 모델이 Qwen3-Embedding-8B라면 모델은 유지하고 저장 차원만 낮추는 안도 4회차에 함께 측정한다.

계산 가중치 메모리는 파라미터 수 × 2바이트로 셈한 값이다. 최대 32K 토큰 입력과 배치 처리에는 추가 메모리가 들고, 실제 GPU 요건은 서빙 엔진과 설정으로 측정한다(D5).

D1

임베딩 서빙

판단 G1 · 12월 말

Qwen3-Embedding-4B를 제품(watsonx.ai)에서 서빙할 수 있나?

  • 확인됨Qwen3-Embedding-4B는 2560차원, 최대 32K 토큰 입력. 출력 차원을 32~2560 사이로 줄일 수 있다(MRL).
  • 확인됨watsonx.ai는 Cloud Pak for Data 5.0부터 커스텀 파운데이션 모델 배포를 지원한다.
  • 확인 필요커스텀 배포가 임베딩 모델 구조를 받는지, GPU 요건(커뮤니티 자료상 A100·H100 80GB급), 임베딩 API 형식.

A지원되면

제품 서빙을 쓴다. 교체 지점 ②에서 주소와 어댑터만 바꾼다. 제품 API 형식이 OpenAI 호환과 다르면 어댑터를 하나 추가한다.

B지원되지 않으면, 순서대로

  1. 사내 게이트웨이에 등록한다. 이미 여러 모델을 서빙하고 있어 가장 빠르다.
  2. 처리량이나 지연이 기준에 못 미치면 등록 조건 변경을 요청하거나 직접 서빙한다(GPU 확보 시, D5).
  3. 모두 어려우면 경량 모델(1024차원)로 낮추고 성능 차이를 평가 결과로 보고한다.
준비 기준OpenAI 호환 /embeddings 경계로 개발하고 게이트웨이 등록을 먼저 요청한다. 제품 확인은 병행한다.

공통 질의와 문서는 같은 모델·버전·차원을 쓴다. 모델이나 차원이 바뀌면 컬렉션을 새로 만들고 전체를 재임베딩한다(02). 모델별 메모리는 06에 있다.

D2

하이브리드 검색

입고 전 IBM 확인 · 입고 직후 실측

watsonx.data에 포함된 Milvus가 BM25 전문 검색을 내장한 버전(2.5 이상)이고, 한국어 분석기를 쓸 수 있나?

  • 확인됨Milvus는 2.5(2024년 12월)부터 Sparse-BM25 전문 검색을 내장했다.
  • 확인 필요입고될 watsonx.data의 Milvus 버전과 한국어 토크나이저 지원. 공개 자료로는 확인하지 못했다.
  • 제공기존 RAG는 BM25 0.3 + 벡터 0.7 가중 하이브리드를 쓴다.

A내장돼 있으면

Milvus 안에서 BM25와 dense 검색을 함께 실행한다. 기존 가중치 0.3/0.7을 출발점으로 다시 측정한다.

B없으면

  • 2.4 이상이면 BM25 sparse 벡터를 자체 생성(한국어 형태소 분석 포함)해 Milvus sparse 필드에 넣는다.
  • 그보다 낮으면 키워드 색인을 별도로 두고 검색 API에서 두 결과를 합친다.
준비 기준sparse 벡터를 직접 만드는 쪽으로 개발한다. 버전과 무관하게 동작하고, A가 확인되면 생성 단계만 제거한다.
D3

제품 입고와 인프라 안정화

판단 G2 · 1월 말

1월 중순 예상대로 입고되고, 2주 안에 on-prem 인프라가 안정화되나?

  • 제공제품 입고는 1월 중순 예상, 운영 오픈 기한은 3월 31일. OCP·watsonx.ai·watsonx.data·LLM 서빙·벡터 DB 안정화는 보장되지 않는다.
  • 계산1월 중순 입고면 제품 위 시험은 약 8주, 2월 중순 입고가 최소 4주를 남기는 경계다(01 그림, 안정화 2주 가정).

A1월 말까지 입고·안정화되면

2월 첫 주에 제품 Milvus로 전환하고, 2월에 UDI 판정·전체 적재·통합·부하 테스트를 한다. 3월에 운영 시나리오와 최종 회귀 평가를 거쳐 3/31에 오픈한다.

B늦어지면

  • 기본: 자체 Milvus로 오픈 후 이관. 제품과 같은 버전의 자체 Milvus로 3/31에 오픈하고, 제품이 안정화되면 청크 정본에서 다시 적재해 전환한다. 검색 API 주소는 그대로라 에이전트 쪽 변경은 없다. 상단 구조도의 ‘Milvus 입고 전/후’가 이 전환이다.
  • 예외: 오픈 연기. 임시 운영이 허용되지 않는 경우에만 제품 안정화와 통합 테스트 이후로 미룬다.
준비 기준자체 Milvus 경로를 오픈까지 유지한다. 입고나 안정화가 늦어져도 개발·평가는 멈추지 않는다.

자체 경로를 유지하는 이유 입고 지연과 on-prem 인프라 안정화는 통제할 수 없는 변수다. 자체 Milvus 경로를 처음부터 유지하면 지연이 오픈 일정으로 번지지 않는다.

파싱 경로

제품 위 시험 중 형식별 판정

UDI가 해당 형식을 자체 기준 이상으로 처리하나?

  • 확인됨IBM 자료는 70종 이상의 형식을 지원한다고 소개한다. 버전별 실제 목록은 해당 버전 문서로 확인해야 한다.
  • 제공현장 검토 결과 지원하지 않는 확장자가 많고, 문서 속 문서·링크 참조 같은 경우를 다루지 못한다(01 문서 계보 화면).

A기준을 넘으면

해당 형식은 UDI로 보낸다(교체 지점 ①). 결과를 공통 형식으로 받아 청킹부터는 같은 경로를 탄다.

B기준에 못 미치면

자체 파서(Docling과 형식별 전용 어댑터)로 처리한다. 고객사 기존 파서 소스도 후보로 함께 비교한다.

준비 기준자체 파서로 개발한다. 제품 안정화 후 같은 표본을 UDI로 처리해 11회차에 형식별로 판정한다.

판단 기준 같은 표본에서 본문, 표, 숫자·단위, 원문 위치가 얼마나 일치하는가. 콘솔의 파싱 비교 화면(03)으로 측정한다.

D5

GPU

판단 G1 · 12월 말

사용 가능한 GPU가 있나?

  • 확인 필요현재 미정. 종류·수량·사용 가능 시점을 모른다. 임베딩 모델 가중치만 4B급 약 8GB, 8B급 약 16GB다(06).

A있으면

리랭커와 OCR을 직접 서빙한다. 필요하면 임베딩도 직접 서빙한다(D1 B-2).

B없으면

임베딩과 리랭커는 게이트웨이를 거친다. OCR은 텍스트 PDF부터 처리하고, 스캔 문서는 범위를 줄이거나 CPU 경량 후보를 시험한다. 현재 콘솔도 OCR은 꺼져 있고 PDF 결과에 누락 가능성 경고를 붙인다.

준비 기준GPU 없이 동작하는 구성으로 개발한다. GPU가 확보되면 서빙 위치만 옮긴다.

Milvus 운영 권한

입고 시

자체 서비스가 watsonx.data Milvus에 컬렉션을 직접 만들고 인덱스를 바꿀 수 있나? 접속 방식과 인증은?

  • 확인 필요접속 방식(gRPC·REST), 인증, 외부 서비스에 주는 권한 범위.

A권한이 있으면

B제품이 관리하면

준비 기준스키마를 선언 파일로 관리한다. 어느 쪽이든 그대로 쓸 수 있고, 제품의 형상 체계를 따르는 방식이다.

평가와의 관계 회차마다 컬렉션을 새로 만들 수 있어야 재구축이 빠르다. B라면 평가용 컬렉션 생성 권한을 별도로 요청한다.
