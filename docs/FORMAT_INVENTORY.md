# 문서 형식 인벤토리: 초기 대상 범위

> 이 문서는 2026-11-12 기준으로 전달받은 대상 형식을 기록한다. 목록은 **출발 범위**다. 이후 새로운 파일 형식과 내부 구조가 계속 추가될 수 있으므로 닫힌 목록이나 전체 지원 보장으로 취급하지 않는다.

## 1. 초기 대상 19개 유형

처음 전달받은 대상 형식은 다음 19개다.

```text
txt, pdf, csv, docx, pptx, xlsx, zip, mht, xlsm, eml,
png, msg, xls, doc, jpg, ppt, htm, docm, log
```

이 목록은 대상 시스템 파일을 이 앱이 직접 스캔한 결과가 아니라 **전달받은 정보**다.

| 보기 편한 분류 | 해당 유형 |
|---|---|
| 문서·발표 | `pdf`, `docx`, `docm`, `doc`, `pptx`, `ppt` |
| 스프레드시트·표 | `xlsx`, `xlsm`, `xls`, `csv` |
| 메일 | `eml`, `msg` |
| 웹·보관 웹페이지 | `mht`, `htm` |
| 이미지 | `png`, `jpg` |
| 텍스트·로그 | `txt`, `log` |
| 압축 | `zip` |

분류는 화면 탐색을 위한 묶음이며 형식별 실제 처리 방식을 같다고 가정하지 않는다. `mht`와 `htm`, `eml`과 `msg`, 구형·신형 Office는 각각 구별한다. **새로운 유형·형태·확장자가 계속 추가될 수 있으므로** 새 발견 항목과 미확인 유형을 별도로 수용한다.

**확인되지 않은 것:** 전체 물량, 확장자별 실제 건수·용량·비율, 원천별 분포, 암호·손상 및 스캔 비율, ZIP 내부·메일 첨부를 펼친 후의 파일 수와 형식. 이 값들은 19개 목록만으로 역산하거나 Mock 통계로 채우지 않는다.

## 2. 요구사항과의 관계

이미지 처리, PDF·Office의 텍스트·표·메타데이터 추출, 실패 단계 재시도·재시작 같은 운영 제어, 끌어 놓기 방식의 파이프라인 구성은 요구사항으로 다뤄지는 주제다. 이 저장소의 화면이 그 기능을 실제로 구현·운영한다는 뜻은 아니다. 파이프라인 운영 모드의 재시도·우회·승인은 브라우저 안 모의 엔진에만 적용된다.

## 3. 가상 데이터, 새 발견 유형, 실제 지원의 구분

- `실험_Cline_vs_OpenCode/dataset/README.md`는 해당 데이터가 생성기로 만든 **가상 데이터**이며, 실험의 `input/B_docs/`가 **36개 파일·18개 형식**이라고 명시한다. 이 샘플은 고객 원천 분포가 아니다.
- 같은 가상 데이터 안내서는 `.msg`를 샘플에 생성하지 못했다고 적는다. 따라서 샘플의 18개 형식을 사용자 발언의 19개로 대체하거나 `.msg`가 대상에 없다고 판단하면 안 된다.
- 앱의 Mock 문서와 가상 파일 추가도 실제 원천 인벤토리가 아니다. 예시 코드에 등장하는 `hwp`, `hwpx`, `heic`, `tiff`, `md` 등을 사용자 제공 19개 목록의 일부로 표시하지 않는다. 다만 이후 실제로 발견되거나 사용자가 추가한 형식은 **새 발견/미확인 항목**으로 기록하고 처리 경로를 열어 둔다.
- 실제 로컬 파서는 텍스트·CSV, Docling PDF·Office, SVG와 래스터 OCR 경로를 제공한다. 각 확장자의 현재 처리는 `backend/app/adapters/registry.py`에서 확인할 수 있다.
- PDF·Office 파싱 품질은 문서 구성에 따라 달라진다. 로컬 EasyOCR 한국어·영어 모델이 준비되면 PDF의 이미지 영역, Office에서 참조한 그림, PNG·JPEG·BMP·TIFF·GIF·WebP 및 SVG 내부 그림을 읽습니다. 최신 지원 범위와 처리 한도는 API·데이터 계약 7절을 참고한다.

## 4. 향후 화면·계약 변경 시 확인할 것

1. 위 19개는 **사용자 제공 출발 범위**로 출처와 함께 보여 주고, 확장자별 건수는 근거가 없으면 `미확인`으로 둔다.
2. 새 파일이나 새 형식을 실제로 발견하면 별도로 추가하되, 사용자 제공 목록에 이전부터 있었다고 바꿔 쓰지 않는다. 확장자만으로 실제 파일 내용과 지원 여부를 확정하지 않는다.
3. Mock 단계·예시 실행, 실제 백엔드 파서 지원, 프로젝트 요구사항을 각각 구분한다. 사용자의 파이프라인 개입 요구를 구현하지 않았다면 개입 결과를 실제 작업 상태처럼 표현하지 않는다.
4. 목록의 근거나 구현 상태가 바뀌면 원본 출처·확인 일자·관련 코드와 계약 문서도 함께 갱신한다.

현재 API와 저장 상태의 자세한 범위는 [API·데이터 계약](API_AND_DATA_CONTRACT.md), Mock과 실제 화면 차이는 [프론트·화면 계약](FRONTEND_AND_INTERACTION_CONTRACT.md), 향후 처리 방안은 [파이프라인·검색 설계](PIPELINE_AND_SEARCH_DESIGN.md)를 참고한다.
