# Unstructured Data Console 인수인계와 로컬 실행 안내

> **기준 시점: 2026-11-12.** 이 문서는 인수인계 시점의 스냅샷이다. 코드·실행 상태·의존성·데이터는 바뀔 수 있으므로 새 세션에서는 아래 확인 순서부터 진행한다. 이 문서는 요구사항이나 고객 환경이 확정되었다는 뜻이 아니다.

## 2026-11-25 (저녁) 추출 결과 읽기 보기, 원문 대조의 DOCX·PPTX 원본, PDF 모델 보류

- **사용자 피드백:** ① 추출 결과 화면이 아쉽다(들여쓰기 등이 맞는지). ② 원문 대조가 '전용 앱에서 원본을 확인하세요'만 보이면 화면의 의미가 없다. ③ 모델은 보류(고객사 PC: i5 10세대 · RAM 16GB).
- **①에 대한 확인:** Docling 결과 자체는 맞다. 합성 DOCX로 제목 단계, 중첩 목록(4칸 들여쓰기), 번호 목록, 표 행·열이 정확히 나오는 것을 확인했다. 어긋나 보인 원인은 표시였다. 결과를 `<pre>`에 가변폭 글꼴로 찍었고, Docling은 표 칸 너비를 글자 수로 맞춰 한글(화면 2칸 폭)이 섞이면 세로선이 어긋난다. 실제 한계는 두 가지다. 병합 셀 값이 칸마다 반복되고(기존 원문 대조 경고), 번호 목록 바로 뒤에 표가 빈 줄 없이 붙는다(일반 Markdown 렌더러는 표를 목록에 붙여 버릴 수 있음. 읽기 보기는 표로 나눈다).
- **바꾼 것(프론트만):**
  - `markdown.ts`(블록·글자 꾸밈 해석, 표 줄 지도, 화면 폭 글자 수), `MarkdownView.tsx`·`markdownView.css`(읽기 보기). 문서 상세 추출 결과에 `읽기 보기 / Markdown 원문` 전환(`ResultBody`, 선택은 브라우저에 기억). 원문 대조 추출 결과 칸도 같은 선택으로 표 줄을 칸으로 그린다(줄 번호·원문 위치 유지).
  - 원문 대조 원본 칸: `compare/OfficeSource.tsx`(DOCX: `docx-preview`, altChunk 끔, 링크 정리, 칸 폭 맞춤 / PPTX: 슬라이드 목록·숨김·메모), `compare/pptx.ts`(PPTX 모델: 자리표시자 상속, 테마 색·글꼴, 그룹, 표 병합, 그림 자르기, 차트 제목·SmartArt 글자, 배경, 마스터 장식). SVG는 `<img>`로. 라벨 `DOCX · 브라우저 재현`과 한계 안내 한 줄.
  - 의존성: `docx-preview` 0.4.1, `jszip` 3.10.1(정확한 버전, `package-lock.json`). 원문 대조에서만 불러오는 별도 묶음(OfficeSource ≈ 37 KB gzip, docx-preview ≈ 21 KB gzip)이라 첫 화면 크기는 그대로다.
  - 서버·API 변경 없음. 원본 파일은 기존 `GET /api/live/documents/{id}/source`로 받는다.
- **PDF 모델:** 사용자 결정으로 보류([결정](DECISIONS.md) 'PDF 모델 설치 보류'). `setup --models`는 그대로 두고 쓰지 않는다. 고객사 PC에서 PDF는 `parser_unavailable`로 남는다.
- **검증:** 프론트 테스트 165개 통과(새 `markdown-view.test.tsx` 9개, `office-source.test.tsx` 6개: 마스터·레이아웃 상속, 테마 밝기(강조 1 50% 어둡게 = `#254061`), 그룹 좌표, 표 병합, 그림 자르기·EMF, 차트 제목, 숨김·메모, PowerPoint 아닌 파일, DOCX 본문·`javascript:` 링크 제거·iframe 없음), 빌드 정상. 백엔드 변경 없음. 실제 서버에 합성 DOCX(제목·중첩 목록·병합 표)와 python-pptx로 만든 PPTX(제목·글머리표·표·차트·그림·글상자·메모)를 올려 Docling으로 파싱하고, Chromium으로 상세(1440px·390px, 가로 넘침 0)·원문 대조·크게 보기를 찍어 확인했다(콘솔 오류 0).
- **확인하지 않은 것:** 실제 고객 DOCX·PPTX의 재현 품질, 고객사 Edge 버전, 큰 파일(수백 쪽 DOCX·수백 장 PPTX)의 그리기 시간.
- **다음:** 고객사 문서 몇 건으로 원문 대조 화면을 보고, 자주 어긋나는 요소(글꼴·도형·표 스타일)를 모은다. 고객사 PDF 처리 위치를 정한다.

- **사용자 보고:** 고객사 PC에서 `huggingface.co` 접속이 막혀 있다(PDF 모델을 받지 못함). XLSM 파서도 필요하다.

- **PDF 모델(바꾼 것):**
  - `check_local.py`: 받기 전에 `huggingface.co`(또는 `HF_ENDPOINT`)의 레이아웃 모델 정보를 10초 제한으로 조회한다. 막혀 있으면 `docling-tools`를 부르지 않고 원인(`프록시가 연결을 막았습니다(403)`, `프록시 인증이 필요합니다(407)`, 시간 초과, 인증서 실패)을 한 줄로 알린다. 이 환경에서 setup 재실행은 5초에 끝난다. `HF_ENDPOINT`가 빈 값이면 하위 프로세스에 넘기지 않는다.

  - `scripts/prepare-offline.py --models-only` → `offline/docling-pdf-models.zip`. `setup --models <ZIP|폴더>`(`scripts/console.py`) → `check_local.py --models-from`. 설치 위치는 콘솔이 모델을 찾는 폴더(`DOCOPS_DOCLING_ARTIFACTS` → `offline/docling-models` → `~/.cache/docling/models`). 묶음 설치가 실패해도 이미 모델이 갖춰져 있으면 요약에 '안 됨'으로 올리지 않는다.
  - 안내 문구: setup 요약·run 시작 화면·PDF 파서 오류·작업 도구 점검·파서 플로우 설치 안내를 모델 ZIP 경로로 바꿨다. `.env.example`에 `DOCOPS_DOCLING_ARTIFACTS`와 주석 처리한 `HF_ENDPOINT`를 넣었다. README에 'huggingface.co가 막힌 PC' 절.
  - 테스트 `test_parser_resilience.py`의 PDF 실측 2건은 모델 폴더가 비어 있어도 건너뛰게 고쳤다(전에는 빈 폴더면 실패).
- **XLSM(바꾼 것):**
  - 라우팅(`registry.DOCLING_FORMATS`), Docling 워크시트 경로(`InputFormat.XLSX`로 변환, 시트 수 한도, 시트·행 위치), 원본 셀 미리보기, OOXML 사본 보정·원문 대조(`OOXML_FORMATS`)에 XLSM을 넣었다. Docling 2.150.0은 `xl/workbook.xml`로 형식을 판별하고 `.xlsm` 확장자도 받는다(실측).
  - `app/vba.py`: `vbaProject.bin`(CFB)의 `VBA/dir`을 [MS-OVBA] 압축 해제로 읽어 모듈 이름·종류·소스·코드 줄 수(`Attribute VB_`·`Option` 줄 제외)·자동 실행 프로시저를 얻는다. 크기 상한(프로젝트 32 MiB, 모듈 소스 4 MiB, 모듈 500개). 매크로는 실행하지 않는다. 압축 해제는 명세 3.2.1·3.2.2 예제로 확인했다.
  - 결과 `warnings`에 `매크로 포함: VBA 모듈 N개(코드 M줄)는 실행하지 않았고 결과 본문에 넣지 않았습니다. 셀 값은 파일에 마지막으로 저장된 값입니다.`(+ 자동 실행 이름). 빈 문서 모듈만 있으면 경고 없음. 코드는 본문에 넣지 않는다.

  - 화면: 파서 플로우 XLSM 설명, 원문 대조의 XLSM 셀 값 미리보기, 지원 형식 안내 문구.

## 2026-11-25 허용 폴더에서 가져오기 (브라우저 파일 첨부가 막힌 고객사 PC)

  - 11-25 `setup`에도 같은 구멍이 남아 있었다. 설치 기록이 없는 PC(예전 실행기로 설치한 PC는 모두 해당)에 Node.js가 없으면 "들어 있는 화면 빌드를 그대로 씁니다"로 옛 빌드를 쓰고, 지금 소스 지문을 기록해 `run`도 통과시켰다. `--offline`은 지문을 보지 않고 dist가 있기만 하면 썼다.
  - 서버가 `index.html`을 캐시 지시 없이 보내 브라우저가 옛 화면을 계속 쓸 여지도 있었다.
  - 사용자 확인: 처음엔 `start.cmd`로 띄웠고, 폴더를 다 지우고 `setup.cmd`→`run.cmd`로 다시 설치해도 옛 화면이 떠서 확인해 보니 **Edge 캐시**였다(옛 서버가 캐시 지시 없이 보낸 `index.html`을 Edge가 다시 묻지 않고 썼다). `start.cmd` 때는 남은 dist가 원인이었을 수 있으나 그 PC의 상태는 확인하지 못했다.
- **바꾼 것:**
  - 화면을 빌드하면 `frontend/dist/docops-build.json`에 그 빌드를 만든 화면 소스(`FRONTEND_INPUTS`와 `src/` 전부)의 파일별 SHA-256(줄바꿈 정규화)과 빌드 시각을 남긴다. `setup`과 `prepare-offline.py`가 쓴다.
  - `setup`은 기록이 지금 소스와 같을 때만 빌드를 건너뛴다. 기록이 없거나 다르면 Node.js로 다시 빌드하고, Node.js가 없거나 `--offline`이면 이유와 함께 멈춘다. 설치 기록(`docops-setup.json`)에는 더 이상 화면 지문을 넣지 않는다.
  - `run`도 같은 기록으로 확인하고, 시작할 때 `[run] 화면 빌드: <시각>`을 보여 준다.
  - 기록에 없는 새 파일은 세지 않는다. 같은 폴더에 덮어써서 남은 옛 소스 때문에 맞는 빌드를 거부하지 않기 위해서다(빌드에 들어가려면 다른 소스가 불러야 하고, 그 소스의 변화로 잡힌다).
  - 오프라인 ZIP은 `frontend/src`를 확장자 제한 없이 넣고, ZIP 안의 소스가 빌드 기록과 맞는지 만들 때 검사한다.
  - `/`(index.html)에 `Cache-Control: no-cache`. 이전 서버에게서 받아 이미 캐시된 화면은 한 번 `Ctrl+F5`로 지워야 한다.
  - `index.html`에 인라인 SVG 아이콘을 넣어 브라우저의 `GET /favicon.ico` 404를 없앴다.
  - 고객사 실행 창의 `GET /health 404`는 이 저장소의 어떤 코드(과거 커밋의 화면 포함)도 보내지 않는다. Milvus 미설정과도 무관하다(설정이 없으면 백엔드는 Milvus에 요청하지 않고, Milvus 확인은 Milvus 주소로 나가므로 콘솔 접속 기록에 찍히지 않는다). 같은 PC의 다른 프로그램이 같은 포트를 확인하는 것으로 보이며, 어떤 프로그램인지는 확인하지 못했다. 별칭 응답은 만들지 않았다(포트 충돌을 가리게 된다). README 문제 해결 표에 찾는 법을 적었다.
- **기존 설치 PC 영향:** 기록이 없는 기존 dist는 처음 한 번 다시 빌드된다(Node.js 필요). 이 변경 전에 만든 오프라인 ZIP은 기록이 없어 `setup --offline`이 멈춘다. ZIP을 다시 만든다.
- **검증:** 백엔드 216개 통과, 11개 건너뜀. `test_console.py`에 옛 빌드 재빌드, Node.js 없을 때 거부, 오프라인 불일치 거부, 덮어쓰기로 남은 파일 무시, run 거부·빌드 시각 표시를 추가했다. Linux에서 기록 없는 dist → `./setup.sh --lite`(다시 빌드) → 재실행(건너뜀) → Node.js 없는 PATH(거부) → `./run.sh`(헤더 `no-cache`, 11-24 화면 문자열이 든 번들 제공)를 확인했다. 오프라인 ZIP은 휠 없이 `build_archive`만 돌려 풀린 폴더에서 기록이 맞는 것과, 기록을 어긋나게 하면 묶음 검증이 실패하는 것을 확인했다. Windows 실기기에서는 확인하지 않았다. 프론트 변경은 `index.html` 아이콘뿐이다(프론트 테스트 146개 통과, Chromium에서 `/favicon.ico` 요청 없음과 404 0건 확인).

- **setup:**
  1. 콘솔이 실행 중이면 멈춘다. 데이터 폴더의 `server.lock`과 8000~8019 포트로 확인한다.

  5. `check_local.py --docling --fetch-models --report <임시 파일>`을 부른다. 빠진 PDF 모델은 `docling-tools models download layout tableformer`로 받는다. `DOCOPS_DOCLING_ARTIFACTS`를 지정했으면 받지 않는다. 이어서 자체 점검을 한다. (같은 날 추가: 받기 전 접속 확인과 `--models` 묶음 설치, 맨 위 절)

## 2026-11-24 OCR: 라이브러리 OCR 끔, 모델 OCR로 교체 진행

## 2. 설계 전제와 작업 원칙

- 기업 내부 비정형 문서 처리 작업을 위한 관리 도구다. **새로운 원천, 문서 형태, 파일 확장자가 계속 추가될 수 있다.** 사전 확정된 원천·확장자 목록을 전제로 설계하지 않는다.
- 전체 물량·확장자 분포·압축 내부 포함 여부는 확인되지 않았다. 논의된 규모를 검증된 물량이나 처리 한도로 고정하지 않는다.
- 장기 목적은 문서를 잘 파싱하고 원문 위치·버전과 문서 간 참조의 근거를 보존해 검색과 에이전트가 활용할 수 있게 하는 것이다. 현재 구현이 그 전체 목적을 충족한다는 의미는 아니다.
- 특히 XLSX의 시트·셀에서 다른 문서를 가리키는 참조, 한국어 문서와 표·숫자·단위, 텍스트/스캔 혼합 PDF가 중요하다. 관계 추출, 파싱, 문서 업무 분류, 모델 판단은 별도 책임이다.
- Mock 프론트에서 시작해 처리 파이프라인(운영·설계)과 **실제로 시험 가능한 간단한 로컬 백엔드**까지 확장했다. 화면을 보면서 다음 방향을 정하는 방식으로 진행한다.
- 단순한 카드 나열이 아닌 실사용 가능한 운영 화면을 목표로 한다. 한국어 UI를 기본으로 하고, 필요한 범위에서 높은 정보 밀도·명확한 계층·반응형·접근성을 고려한다.
- 작업을 병렬화하더라도 파일 소유 범위를 정하고 통합 후 테스트·독립 검토를 수행한다.
- 모든 문서를 대형 LLM으로 일괄 분류하는 방식은 지양한다. 빠른 판단 모델은 **후보**일 뿐, 필요한 판단·한국어 정확도·연동 방식을 먼저 평가해야 한다.
- 대상 환경에는 OpenAI 호환 게이트웨이(`base_url`, `api_key`, `model_id`)로 쓸 수 있는 모델이 있다. 앱은 `.env`의 `MODEL_*`·`MODEL2_*` 값으로 연결 확인과 모델 목록 조회만 한다. 모델별 용도·성능·사용 조건은 환경에서 검증한다. 키나 주소를 추측해 기록하지 않는다.

| 실제 파일 처리 | 선택·드롭 즉시 로컬 백엔드로 업로드, 별도 버튼으로 비동기 파싱, 상태·오류·결과 확인 | 실제로 파일을 로컬에 저장한다. Mock 탐색과 목록이 분리되어 있다. |
| 구조 분석 | 실제 원본을 열어 문서 계보(압축 항목·메일 첨부·Office/HWP 내장 개체·PDF 첨부)와 링크·참조 후보(하이퍼링크, 외부 통합문서 셀 참조, 필드 연결, 공유 폴더 경로, 문서번호), 암호화·DRM 의심·확장자 불일치·매크로를 표시. 문서별 버튼과 전체 분석, 원본 대비 발견 문서 배율 | 사용자가 누를 때만 실행. 링크 대상 문서와의 실제 연결 확인, PDF 본문 텍스트 속 문서번호, PPT 내장 개체는 아직 아님 |
| 모델 연결 | 생성 모델 연결 1~2개와 임베딩 연결을 화면에서 편집·저장(저장 전 확인 가능, `.env`보다 우선, 재시작 없이 반영), 버튼으로 연결 확인과 모델 목록 조회 | 키 값은 화면·응답에 나오지 않는다. 저장값은 `runtime/settings/connections.json`(0600). 문서 처리 단계에서 모델을 호출하지는 않는다. |

Mock API 오류나 로딩 중에도 실제 처리 탭으로 이동할 수 있으며, 실제 API의 실패는 별도로 나타난다. 대시보드 위젯·파이프라인 **미리보기 설정**은 브라우저의 localStorage에 남지만 실 데이터나 운영 설정이 아니다.

### 실제 파서 범위

- `TXT`, `CSV`, `MD`, `LOG`는 기본 파이썬 파서 경로가 있다. 텍스트 디코딩은 UTF-8 BOM 포함 또는 CP949를 시도한다. CSV는 Markdown 표로 출력한다.
- `PDF`, `DOCX`, `PPTX`, `XLSX`는 선택적으로 설치한 Docling 경로로 연결된다. 이전 개발 세션에서는 **합성 DOCX와 텍스트 PDF**를 Docling 2.150.0으로 시험했다. PPTX·XLSX는 어댑터가 있으나 실제 문서에 대한 품질 검증이 필요하다.
- 경로는 확장자로 고르지만, 파서 전에 내용 서명으로 DRM·암호·형식 불일치를 걸러 `error_code`로 남긴다(2026-11-19). DOCX·XLSX·PPTX는 기호 글꼴·첨자 사본 보정과 원문 대조(`fidelity`)를 거친다. 복잡한 표와 원문 페이지·시트·셀 위치가 정확하게 추출된다고 보장하지 않는다.
- 스캔 쪽과 그림의 글자는 연결한 문서 OCR 모델(OpenAI 호환 비전 API)로만 읽는다(2026-11-24 결정, 라이브러리 OCR 없음). 대상은 PDF의 글자 층 없는 쪽과 큰 그림, Office·SVG 속 그림, PNG·JPEG·BMP·TIFF·GIF·WebP다. 적용 여부는 각 실행 이력에서 확인한다.
- HWP/HWPX·ZIP 내부 분리·메일 첨부·kordoc·Excel 외부 참조 연결·검색 인덱싱은 실제 파서에 연결되지 않았다. 지원하지 않는 형식은 `unsupported`로 드러난다.

### 파일과 로컬 상태

- 실제 원본 `runtime/uploads/`, 결과 `runtime/results/`, 문서·상태·이력 `runtime/documents.sqlite3`이 기본 저장 위치다. `DOCOPS_RUNTIME_DIR` 설정에 따라 위치가 달라질 수 있다.
- 기준 시점의 로컬 실제 처리 목록에는 시각 검증용으로 만든 합성 `docops_synthetic_review.txt` 1건이 보였다. 이 파일을 고객 문서나 실제 운영 데이터로 해석하지 않는다. 사용자가 이후 파일을 추가했을 수 있으므로 `runtime/` 전체를 테스트 데이터로 취급하지 않는다.
- 실제 업로드 원본·결과·파일명은 로컬 저장소에 남는다. 현재 문서 삭제 API/화면은 없다. `.gitignore`에는 `runtime/`, 가상환경, `node_modules/`, `dist/`, 환경변수 파일이 포함돼 있다. Git 제외가 백업·접근제어를 대신하지는 않는다.
- 실제 파일, 추출 결과, 자격 증명, 고객 정보를 예시·테스트·GitHub에 넣지 않는다. 새 검증에는 합성 파일이나 명시적으로 사용이 허용된 자료를 쓴다.

## 4. 경로와 로컬 실행

아래 명령은 모두 프로젝트 루트(이 저장소를 받은 폴더) 기준이다. 경로에 공백이 있으면 따옴표로 감싼다. Windows 대상 PC로 옮길 때는 [README](../README.md)의 "Windows PC에서 실행"을 따른다.

이미 켜진 서버가 있는지 먼저 확인한다. 아래 조회는 서버를 변경하지 않는다.

```bash
lsof -nP -iTCP:5173 -sTCP:LISTEN
lsof -nP -iTCP:8000 -sTCP:LISTEN
curl -fsS http://127.0.0.1:5173/api/health
```

기준 시점에는 프론트 5173, 백엔드 8000이 루프백에서 응답했고 `health`는 `mode: local`, `mock_data: available`, `live_processing: available`을 반환했다. 프로세스 상태는 세션이 끝난 뒤 달라질 수 있다. 포트 점유자를 모르면 무작정 종료하거나 다른 서버를 같은 데이터 경로로 중복 기동하지 않는다.

### 백엔드

프로젝트 루트에서 별도 터미널을 연다. 처음 설치할 때만 가상환경과 의존성을 준비한다.

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn main:app --host 127.0.0.1 --port 8000
```

Docling을 사용할 경우 별도로 설치한다. 설치에는 패키지 저장소 접근이 필요할 수 있으나, 문서 처리 시에는 모델의 외부 다운로드를 시도하지 않도록 코드가 오프라인 모드를 설정한다.

```bash
pip install -r requirements-docling.txt
```

PDF는 미리 준비된 로컬 모델 경로가 필요하다. 기본 경로는 `~/.cache/docling/models`이며, 다른 위치를 사용하면 서버 시작 전에 `DOCOPS_DOCLING_ARTIFACTS` 또는 `DOCLING_ARTIFACTS_PATH`를 설정한다. 이 환경에서는 기준 시점에 기본 캐시와 Docling 2.150.0이 확인됐다. 다른 환경에서도 같다고 가정하지 않는다. 자세한 제한과 API는 [백엔드 안내서](../backend/README.md)를 본다.

### 프론트엔드

다른 터미널에서 프로젝트 루트부터 실행한다.

```bash
cd frontend
npm ci
npm run dev
```

[Vite 로컬 화면](http://127.0.0.1:5173/)을 열면 `/api`가 백엔드의 `127.0.0.1:8000`으로 프록시된다. `npm ci`와 패키지 설치는 의존성을 다시 설치하므로 실행 중인 다른 작업과 충돌하지 않도록 필요할 때만 수행한다. 앱 사용 중에는 두 서버가 필요하다.

## 5. 작업 상태, 진단과 검증

- API 상태: `GET /api/health`. Mock 데이터: `GET /api/data`. 실제 로컬 목록: `GET /api/live/documents`. 실제 목록에는 사용자 파일명이 포함될 수 있으므로 불필요하게 출력·공유하지 않는다.
- 실제 처리 상태는 `uploaded`, `processing`, `completed`, `failed`, `unsupported`다. `processing`에는 **실제 처리와 대기**가 모두 포함된다. 업로드만으로는 파싱하지 않는다.
- 실제 파일 여러 개를 순차 업로드하는 도중 다른 탭으로 이동하면 화면이 해제되어 일부만 전송되거나 실패 경로에서 후속 요청이 계속될 수 있다. 이미 요청한 파일은 서버에 남을 수 있으므로 돌아와 실제 목록을 확인한다. 일괄 업로드의 지속·부분 성공·재개 처리는 아직 구현하지 않았다.
- 단일 전용 워커와 기본 64건 메모리 대기열을 쓴다. 대기열이 가득 차면 처리 요청은 HTTP 503이며 거절 이력이 남는다. 동일 문서 중복 처리 요청은 HTTP 409다. 운영용 내구성 큐가 아니다.
- 텍스트 입력은 파일당 100 MiB, CSV는 100만 행·1,000열, 셀당 4,194,304자, 물리적 한 줄당 8,388,608자, UTF-8 Markdown 결과 100 MiB까지 처리합니다.
- 재처리 중·실패 후에도 마지막 성공 결과는 보존되며 결과 응답의 `is_stale: true`로 구분한다. 새 결과가 성공하면 `false`다. OCR 미적용 PDF 성공 결과에는 `warnings`의 OCR 미적용 경고가 포함된다.
- 정상 종료 시 대기 작업은 실패 이력으로 바뀌고 재시도가 필요하다. 진행 중 작업은 최대 5초 기다리며 작업이 남으면 워커가 끝날 때까지 런타임 잠금을 유지한다. 프로세스가 먼저 끝나면 재시작 시 남은 처리 중 상태가 실패로 복구된다. 작업은 자동 재실행되지 않는다.
- 결과가 없는 경우와 저장된 결과 파일/메타데이터가 손상된 경우 모두 HTTP 409가 발생한다. 현재 `frontend/src/api/live.ts`는 오류 상세 문자열로 구분한다. 문구 변경만으로 화면 처리가 달라질 수 있으므로 API/프론트 테스트를 함께 확인한다.
- 로컬 전용 바인딩과 Origin 검사는 운영 인증·인가가 아니다. 이 프로토타입은 사용자 인증, 문서별 권한, 다중 사용자 운영을 제공하지 않는다.

자동 검증은 프로젝트 루트에서 각각 실행한다. 테스트는 합성 데이터와 격리된 임시 저장소를 사용하도록 작성돼 있다. 의존성이 없다면 백엔드 테스트용 `requirements-dev.txt`를 설치해야 한다.

```bash
cd frontend
npm test
npm run build
```

```bash
cd backend
source .venv/bin/activate
pip install -r requirements-dev.txt
python -m pytest -q
```

2026-11-12 구조 분석 추가 후 프론트 테스트 31개, 백엔드 테스트 26개(구조 분석·모델 연결·Windows 잠금 포함)와 프론트 빌드가 통과했다. 번들 500kB 초과 안내는 React Flow 포함에 따른 것이다. 백엔드 TestClient 관련 비차단 폐기 예정 경고가 있다.

### 자주 보는 증상

| 증상 | 먼저 확인할 것 |
|---|---|
| 화면이 열리지 않음 | 5173 포트와 Vite 상태, 프론트 빌드 오류. 실제/Mock 데이터 로딩 실패를 화면 전체 오류와 혼동하지 않는다. |
| 실제 문서 목록/API가 실패 | 8000 포트, `/api/health`, Vite 프록시, 서버 콘솔. 원본 파일이나 SQLite를 지우기 전에 저장 경로와 실행 중 작업부터 확인한다. |
| Docling 처리 실패 | Docling 선택 의존성, PDF용 로컬 모델 경로, 파일 상태와 백엔드 오류. 모델을 임의로 외부에서 내려받았다고 가정하지 않는다. |
| PDF 완료 후 내용 일부가 빠짐 | 해당 실행의 OCR 설정과 빈 페이지 경고를 확인한다. 모델 위치는 README의 OCR 설정을 따른다. |
| 처리 결과가 이전 내용으로 보임 | 문서 상태와 `is_stale`을 확인한다. 재처리 중·실패 후 마지막 성공 결과가 의도적으로 남는다. |
| 처리 요청이 503 | 대기열 포화 또는 워커 미사용 상태다. 오류·이력을 확인하고 나중에 다시 요청한다. API 요청을 무한 반복하지 않는다. |
| 새 형식이 미지원 | Mock 파이프라인에 형식 카드가 있어도 실제 어댑터가 있는 것은 아니다. 실제 라우팅은 `backend/app/adapters/registry.py`를 확인한다. |

## 6. 다음에 이어갈 후보와 미결정 사항

다음 항목은 **추천 순서이지 사용자가 확정한 변경 지시가 아니다.** 다음 요청을 먼저 따르고, 독립적으로 할 수 있는 준비와 검증을 진행한다.

1. **파서 성능 측정**: 형식별로 본문·표·숫자·원문 위치가 얼마나 맞는지 재는 틀을 합성 샘플로 먼저 만든다(골드셋 버전 관리 기능은 만들지 않기로 했다). 구조 분석 결과(하위 문서·이미지 포함·암호화)를 측정 대상 선정에 쓴다.
2. 여러 파일을 업로드하는 동안 작업 탭을 벗어났을 때의 지속·취소·부분 성공·재개 동작을 먼저 명확히 하고 검증한다. 현재는 일부만 전송될 수 있다.
3. 실제 파일 처리 상태를 대시보드에 연결할 범위와 Mock/실제 전환 방식을 화면을 보면서 구체화한다. 지금은 두 데이터가 분리돼 있다.
4. 대표 합성 PDF·오피스·스캔 파일로 파싱 품질을 평가한다. OCR 후보 및 kordoc은 도입 전 한국어·영문, 표·문서번호·숫자·단위와 속도/자원/오류를 비교한다. 실제 고객 샘플 사용과 보관은 허용된 범위에서만 한다.
5. 구조 분석으로 찾은 링크·문서번호 후보를 업로드된 다른 문서와 실제로 맞춰 보는 연결 확인(대상 발견·미발견·후보 여러 개)과 순환 탐지. 현재 관계도 화면은 Mock이다.
6. 결과 부재와 저장 손상 등에 안정적인 오류 코드를 도입해 텍스트에 의존하는 프론트 분기를 줄인다. 기존 클라이언트와 테스트의 호환성을 같이 정한다.
7. 구조 분석의 형식 판별 결과를 파서 경로 선택에 연결하고(지금은 확장자 기준), 변경·삭제 추적을 설계한다. 파일 확장자 종류가 늘어날 수 있다는 전제를 유지한다.
8. 분류가 필요해지면 LLM 분류가 아니라 판단 결과만 돌려주는 System 1 형 모델을 우선 검토한다. 대상 환경 게이트웨이의 API·인증·허용 자원과 그 모델의 접속·성능을 확인한 뒤 어댑터를 정한다. API 키는 프론트·코드·문서에 넣지 않는다.
9. 실제 운영 범위가 정해지면 권한·비밀 관리, 보존/삭제, 내구성 대기열, 관측성, 인프라·배포 및 검색 연계를 별도로 설계한다. 현재 로컬 프로토타입이 이를 충족한다고 가정하지 않는다.

고객 원천별 파일 분포, 파싱 정확도 기준, 실제 검색·에이전트 계약, 원문 권한·버전 전달, 게이트웨이 반입 가능 모델, 스캔 비율과 인프라 한도는 아직 확인되지 않았다. 이 때문에 구현을 무조건 멈추기보다, 가상의 사례·교체 가능한 경계·명시적인 미확인 상태로 진행한다.
