# Unstructured Data Console 인수인계와 로컬 실행 안내

이 문서는 현재 상태와 실행·점검 방법만 담는다. 세션별 작업 기록은 [작업 이력](HISTORY.md)으로 옮겼다(필요할 때만 연다). §1 이후는 2026-11-12에 쓴 실행 안내가 바탕이다. 코드·실행 상태·의존성·데이터는 바뀔 수 있으므로 새 세션에서는 §1의 확인 순서부터 진행한다. 이 문서는 요구사항이나 고객 환경이 확정되었다는 뜻이 아니다.

## 0. 현재 상태 (2026-11-28)

### 들어가 있는 것

- 설치·실행: `setup`·`run`(로직은 `scripts/console.py`). 기본 설치에 Docling 포함, `--lite`에서만 빠진다. 화면 빌드는 `frontend/dist/docops-build.json`의 빌드 기록이 지금 소스와 같을 때만 다시 쓴다.
- 파서: Docling(DOCX·DOCM·PPTX·XLSX·XLSM, HTM·MHT, PDF 모델이 있으면 PDF), PDF 모델이 없으면 글자 층만 읽는 `pdf-text`, 텍스트·CSV(원천 형식 지정으로 다시 파싱), EML(`python-eml`)·MSG(`python-msg`). 처음 받은 19개 형식 중 DOC·XLS·PPT·ZIP만 경로가 없다. 스캔 쪽과 그림 글자는 연결한 문서 OCR 모델로만 읽는다.
- 검수: 자동 대조 원장(`qc_runs`·`qc_findings`), 판정 상태(검수 필요 → 판정 불가 → 통과 후보, 자동 통과 없음), 검수 요청(V번호), 숨은 글자 층·차트 캐시 대조. 대조 규칙이 바뀌면 서버 시작 때 최신 성공 실행을 다시 대조한다(`DOCOPS_QC_REVERIFY`). 규칙 키는 대조 코드의 실행 구조(AST) 지문이라 주석·docstring만 고친 업데이트로는 다시 대조하지 않는다. 다시 대조는 사용자가 요청한 파싱을 먼저 보낸다. 원본이 400만 자를 넘으면 읽은 범위까지만 대조하고 나머지는 '확인하지 않은 범위'(판정 불가)로 센다.
- 규모(합성 1,500건, 이 Mac 측정): 파싱+대조 문서당 약 0.24초(코어 하나), 대조 코드가 바뀐 뒤 첫 시작의 다시 대조 1,500건 약 2분. Windows 고객사 PC로는 재지 않았다.
- 작업 에이전트 도구(MCP·CLI): 파싱 대행이 아니라 검수 보조다. [작업 에이전트 도구](AGENT_TOOLS.md).
- 허용 폴더에서 가져오기: 브라우저 파일 첨부가 막힌 PC용. 가져오기는 저장만 하고 파싱은 사용자가 누를 때 접수한다.

### 고객사 PC (사용자 확인 기준)

- 사양 i5 10세대 · RAM 16GB. Docling PDF 모델 설치는 보류해서 PDF는 `pdf-text`로 읽는다.
- `huggingface.co`는 막혀 있고 PyPI·npm은 열려 있다. WSL은 막혀 있고 Git Bash는 쓸 수 있다.
- 브라우저 파일 첨부·전송을 보안 프로그램이 막는다. 허용 폴더 가져오기를 쓰며, 보안 정책이 이 방식을 허용하는지는 확인하지 않았다.
- 게이트웨이에 OCR 모델이 언제 올라갈지 정해지지 않았다. 그 전까지 스캔·이미지 글자는 추출되지 않는다.
- 프로젝트 위치는 `C:\Users\USER\Desktop\vswrk\unstructured-parser-control-plane`(사용자 제공). `.env`를 비워 두면 그 아래 `samples`가 허용 폴더다.
- 업데이트: 콘솔을 닫고 ZIP을 덮어쓴 뒤 `setup.cmd` → `run.cmd`, 브라우저는 한 번 `Ctrl+F5`. 처음 시작할 때 기존 문서를 다시 대조하므로 문서가 많으면 깔때기의 '규칙 변경 · 다시 대조 n/N'이 끝날 때까지 기다린다.

### 확인하지 않은 것

- 고객사 Windows PC와 실제 고객 문서: 시작 시 다시 대조에 걸리는 시간, 자동 대조의 오통과·오탐, 검수 시간, 사내 모델이 작업 도구를 잘 고르는지, Edge에서의 원문 대조 화면.
- 실제 OCR 모델 출력: 숨은 글자 층 대조의 항목 이름 표기, OCR을 붙인 스캔 쪽(가짜 OCR 서버로만 확인).
- Excel이 저장한 실제 차트(날짜 범주·여러 영역·이름 정의), 1,001시트 실제 통합문서의 원장 크기, Outlook이 저장한 실제 MSG, Word·IE가 저장한 실제 HTM·MHT, 실제 DOCM, TAR.
- 흰 글자·클리핑·덮어쓰기 같은 다른 숨김.
- 실제 PDF 모델 파일로 모델 ZIP 묶기·설치.

### 최근 작업에서 나온 다음 후보

추천일 뿐 사용자가 확정한 지시가 아니다.

1. 첫 방문 보정: 무작위 20~30건과 알려진 실패, 중요 오류의 정의를 고객 검수자와 정한다.
2. 실제 고객 문서 몇 건으로 자동 대조 오탐을 보고 기준을 다듬는다. 틀림으로 확인된 유형을 모아 파서 개선 목록으로 만든다.
3. 숨은 글자 층 영역만 골라 OCR 모델로 다시 읽는다.
4. 표 헤더 계보·병합 범위, 표 구조와 읽는 순서 대조.
5. XLSX 시트·셀 주소를 청크 위치로 쓴다.
6. OCR 캐시 영속화와 PDF 변환 프로세스 격리(Windows 측정 후), BOM 없는 UTF-16, ZIP 목록 모드.
6-1. 남은 형식: 구형 Office(DOC·XLS·PPT)는 LibreOffice 없이 순수 파이썬으로(XLS는 BIFF 셀 값, DOC·PPT는 글자 층부터), MSG의 압축 RTF 본문([MS-OXRTFCP] 풀기 + RTF 글 추출), ZIP 안 파일을 하위 문서로 등록할지.
6-2. 이전 규칙 원장 상세(`qc_findings`)는 지우지 않아 대조 코드가 바뀔 때마다 쌓인다(측정 1,500건: 회당 +64 MiB, 그중 의심점 행의 87%가 잘린 CSV 오탐이었고 이것은 고쳤다. 고친 뒤 크기는 다시 재지 않음). 고객사 문서 수·업데이트 빈도를 보고 정리 정책을 정한다. 파싱 병렬화(프로세스)는 그 규모를 본 뒤.
7. 작업 에이전트 2~4단계: 청킹·임베딩 평가, Milvus 적재(계획→실행 분리, 실행만 승인), 검색.
8. 고객사 PDF를 어디서 어떤 방식으로 파싱할지 정한다.

## 1. 새 세션에서 먼저 할 일

1. 사용자의 최신 요청과 이 파일, [프로젝트 README](../README.md), [아키텍처](ARCHITECTURE.md)를 읽고 현재 작업 범위를 확인한다. 기존 구현을 새로 만들기 전에 관련 코드와 테스트부터 살펴본다.
2. 프로젝트 폴더와 Git 상태를 확인한다. 공개 저장소 `SeoJHeasdw/unstructured-parser-control-plane`의 `main`에 올라가 있다. 고객 데이터가 들어가는 시점에는 저장소를 분리할 수 있으므로 실제 문서·추출 결과·고객 식별 정보는 커밋하지 않는다.
3. 실제 파일 처리와 Mock을 구별한다. Mock에 표시된 통계·문서·파이프라인은 실제 처리 현황이 아니다. 실 파일 목록도 Mock 대시보드에 자동 반영되지 않는다.
4. 서비스가 이미 켜져 있는지 확인한다. 실제 파일이 처리 중일 수 있으니 소유자를 확인하지 않고 서버를 재시작하거나 프로세스를 종료하지 않는다. `runtime/`과 브라우저 저장 설정을 임의로 지우거나 초기화하지 않는다.
5. 요구가 파싱·검색·모델과 관계된다면 실제 지원 범위와 테스트를 다시 확인한다. 문서 형식이나 원천의 전체 목록을 알고 있다고 가정하지 않는다.
6. 화면 변경 시 사용자가 직접 확인할 수 있는 동작과 시각적 완성도를 함께 검토한다. 자동 테스트 통과만으로 실제 화면 품질을 단정하지 않는다.

## 2. 설계 전제와 작업 원칙

- 기업 내부 비정형 문서 처리 작업을 위한 관리 도구다. **새로운 원천, 문서 형태, 파일 확장자가 계속 추가될 수 있다.** 사전 확정된 원천·확장자 목록을 전제로 설계하지 않는다.
- 전체 물량·확장자 분포·압축 내부 포함 여부는 확인되지 않았다. 논의된 규모를 검증된 물량이나 처리 한도로 고정하지 않는다.
- 장기 목적은 문서를 잘 파싱하고 원문 위치·버전과 문서 간 참조의 근거를 보존해 검색과 에이전트가 활용할 수 있게 하는 것이다. 현재 구현이 그 전체 목적을 충족한다는 의미는 아니다.
- 특히 XLSX의 시트·셀에서 다른 문서를 가리키는 참조, 한국어 문서와 표·숫자·단위, 텍스트/스캔 혼합 PDF가 중요하다. 관계 추출, 파싱, 문서 업무 분류, 모델 판단은 별도 책임이다.
- Mock 프론트에서 시작해 처리 파이프라인(운영·설계)과 **실제로 시험 가능한 간단한 로컬 백엔드**까지 확장했다. 화면을 보면서 다음 방향을 정하는 방식으로 진행한다.
- 단순한 카드 나열이 아닌 실사용 가능한 운영 화면을 목표로 한다. 한국어 UI를 기본으로 하고, 필요한 범위에서 높은 정보 밀도·명확한 계층·반응형·접근성을 고려한다.
- 작업을 병렬화하더라도 파일 소유 범위를 정하고 통합 후 테스트·독립 검토를 수행한다.
- 모든 문서를 대형 LLM으로 일괄 분류하는 방식은 지양한다. 빠른 판단 모델은 **후보**일 뿐, 필요한 판단·한국어 정확도·연동 방식을 먼저 평가해야 한다.
- 대상 환경에는 OpenAI 호환 게이트웨이(`base_url`, `api_key`, `model_id`)로 쓸 수 있는 모델이 있다. 앱은 `.env`의 `MODEL_*`·`MODEL2_*` 값으로 연결 확인과 모델 목록 조회만 한다. 모델별 용도·성능·사용 조건은 환경에서 검증한다. 키나 주소를 추측해 기록하지 않는다.

### 실제 파서 범위

실제 라우팅은 `backend/app/adapters/registry.py`가 정한다. 경로는 확장자로 고르고, 파서 전에 내용 서명으로 DRM·암호·형식 불일치를 걸러 `error_code`로 남긴다.

- `TXT`, `MD`, `LOG`는 `python-text`, `CSV`는 `python-csv`(Markdown 표). 인코딩·구분자 판정 근거를 실행 `evidence`에 남기고, 확정하지 못하면 판정 불가로 둔다. 원천 형식(인코딩·구분자)을 지정해 다시 파싱할 수 있다.
- `DOCX`, `DOCM`, `PPTX`, `XLSX`, `XLSM`은 Docling. OOXML은 기호 글꼴·첨자 사본 보정과 원문 대조(`fidelity`)를 거친다. XLSM 매크로는 실행하지 않는다.
- `PDF`는 PDF 모델이 있으면 Docling, 없으면 글자 층만 읽는 `pdf-text`.
- `EML`은 `python-eml`, `MSG`는 `python-msg`(둘 다 헤더·본문·첨부 목록, 첨부 본문은 읽지 않음. MSG의 압축 RTF 본문은 아직 읽지 않음), `SVG`는 `python-svg`.
- `DOCM`은 DOCX 경로(매크로 미실행), `HTM`·`HTML`·`MHT`·`MHTML`은 Docling HTML 처리기(인코딩 근거를 실행에 남김, 외부 자원 안 엶).
- 스캔 쪽과 그림의 글자는 연결한 문서 OCR 모델(OpenAI 호환 비전 API)로만 읽는다. 대상은 PDF의 글자 층 없는 쪽과 큰 그림, Office·SVG 속 그림, PNG·JPEG·BMP·TIFF·GIF·WebP(`ocr-model`)다. 적용 여부는 각 실행 이력에서 확인한다.
- 복잡한 표와 원문 쪽·시트·셀 위치가 정확하게 추출된다고 보장하지 않는다. 파싱 성공은 품질 보증이 아니며, 자동 대조와 사람 검수가 따로 있다.
- HWP/HWPX·구형 Office(DOC·XLS·PPT)·ZIP 내부 분리·메일 첨부 본문·MSG의 압축 RTF 본문·kordoc·Excel 외부 참조 연결·검색 인덱싱은 실제 파서에 연결되지 않았다. 지원하지 않는 형식은 `unsupported`로 드러난다.

### 파일과 로컬 상태

- 실제 원본 `runtime/uploads/`, 결과 `runtime/results/`, 문서·상태·이력 `runtime/documents.sqlite3`이 기본 저장 위치다. `DOCOPS_RUNTIME_DIR` 설정에 따라 위치가 달라질 수 있다.
- 기준 시점의 로컬 실제 처리 목록에는 시각 검증용으로 만든 합성 `docops_synthetic_review.txt` 1건이 보였다. 이 파일을 고객 문서나 실제 운영 데이터로 해석하지 않는다. 사용자가 이후 파일을 추가했을 수 있으므로 `runtime/` 전체를 테스트 데이터로 취급하지 않는다.
- 실제 업로드 원본·결과·파일명은 로컬 저장소에 남는다. 현재 문서 삭제 API/화면은 없다. `.gitignore`에는 `runtime/`, 가상환경, `node_modules/`, `dist/`, 환경변수 파일이 포함돼 있다. Git 제외가 백업·접근제어를 대신하지는 않는다.
- 실제 파일, 추출 결과, 자격 증명, 고객 정보를 예시·테스트·GitHub에 넣지 않는다. 새 검증에는 합성 파일이나 명시적으로 사용이 허용된 자료를 쓴다.

## 4. 경로와 로컬 실행

보통은 `setup`으로 설치하고 `run`으로 띄운다([README](../README.md)). 아래는 개발 중에 백엔드와 Vite 화면을 따로 띄울 때의 방법이다. 명령은 모두 프로젝트 루트(이 저장소를 받은 폴더) 기준이다. 경로에 공백이 있으면 따옴표로 감싼다. Windows 대상 PC로 옮길 때는 [README](../README.md)의 "Windows PC에서 실행"을 따른다.

이미 켜진 서버가 있는지 먼저 확인한다. 아래 조회는 서버를 변경하지 않는다.

```bash
lsof -nP -iTCP:5173 -sTCP:LISTEN
lsof -nP -iTCP:8000 -sTCP:LISTEN
curl -fsS http://127.0.0.1:5173/api/health
```

기준 시점에는 프론트 5173, 백엔드 8000이 루프백에서 응답했고 `health`는 `mode: local`, `mock_data: available`, `live_processing: available`을 반환했다. 프로세스 상태는 세션이 끝난 뒤 달라질 수 있다. 포트 점유자를 모르면 무작정 종료하거나 다른 서버를 같은 데이터 경로로 중복 기동하지 않는다.

### 백엔드

프로젝트 루트에서 별도 터미널을 연다. 처음 설치할 때만 가상환경과 의존성을 준비한다.

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn main:app --host 127.0.0.1 --port 8000
```

Docling을 사용할 경우 별도로 설치한다. 설치에는 패키지 저장소 접근이 필요할 수 있으나, 문서 처리 시에는 모델의 외부 다운로드를 시도하지 않도록 코드가 오프라인 모드를 설정한다.

```bash
pip install -r requirements-docling.txt
```

PDF는 미리 준비된 로컬 모델 경로가 필요하다. 기본 경로는 `~/.cache/docling/models`이며, 다른 위치를 사용하면 서버 시작 전에 `DOCOPS_DOCLING_ARTIFACTS` 또는 `DOCLING_ARTIFACTS_PATH`를 설정한다. 이 환경에서는 기준 시점에 기본 캐시와 Docling 2.150.0이 확인됐다. 다른 환경에서도 같다고 가정하지 않는다. 자세한 제한과 API는 [백엔드 안내서](../backend/README.md)를 본다.

### 프론트엔드

다른 터미널에서 프로젝트 루트부터 실행한다.

```bash
cd frontend
npm ci
npm run dev
```

[Vite 로컬 화면](http://127.0.0.1:5173/)을 열면 `/api`가 백엔드의 `127.0.0.1:8000`으로 프록시된다. `npm ci`와 패키지 설치는 의존성을 다시 설치하므로 실행 중인 다른 작업과 충돌하지 않도록 필요할 때만 수행한다. 앱 사용 중에는 두 서버가 필요하다.

## 5. 작업 상태, 진단과 검증

- API 상태: `GET /api/health`. Mock 데이터: `GET /api/data`. 실제 로컬 목록: `GET /api/live/documents`. 실제 목록에는 사용자 파일명이 포함될 수 있으므로 불필요하게 출력·공유하지 않는다.
- 실제 처리 상태는 `uploaded`, `processing`, `completed`, `failed`, `unsupported`다. `processing`에는 **실제 처리와 대기**가 모두 포함된다. 업로드만으로는 파싱하지 않는다.
- 실제 파일 여러 개를 순차 업로드하는 도중 다른 탭으로 이동하면 화면이 해제되어 일부만 전송되거나 실패 경로에서 후속 요청이 계속될 수 있다. 이미 요청한 파일은 서버에 남을 수 있으므로 돌아와 실제 목록을 확인한다. 일괄 업로드의 지속·부분 성공·재개 처리는 아직 구현하지 않았다.
- 단일 전용 워커와 기본 64건 메모리 대기열을 쓴다. 대기열이 가득 차면 처리 요청은 HTTP 503이며 거절 이력이 남는다. 동일 문서 중복 처리 요청은 HTTP 409다. 운영용 내구성 큐가 아니다.
- 텍스트 입력은 파일당 100 MiB, CSV는 100만 행·1,000열, 셀당 4,194,304자, 물리적 한 줄당 8,388,608자, UTF-8 Markdown 결과 100 MiB까지 처리합니다.
- 재처리 중·실패 후에도 마지막 성공 결과는 보존되며 결과 응답의 `is_stale: true`로 구분한다. 새 결과가 성공하면 `false`다. OCR 미적용 PDF 성공 결과에는 `warnings`의 OCR 미적용 경고가 포함된다.
- 정상 종료 시 대기 작업은 실패 이력으로 바뀌고 재시도가 필요하다. 진행 중 작업은 최대 5초 기다리며 작업이 남으면 워커가 끝날 때까지 런타임 잠금을 유지한다. 프로세스가 먼저 끝나면 재시작 시 남은 처리 중 상태가 실패로 복구된다. 작업은 자동 재실행되지 않는다.
- 결과가 없는 경우와 저장된 결과 파일/메타데이터가 손상된 경우 모두 HTTP 409가 발생한다. 현재 `frontend/src/api/live.ts`는 오류 상세 문자열로 구분한다. 문구 변경만으로 화면 처리가 달라질 수 있으므로 API/프론트 테스트를 함께 확인한다.
- 로컬 전용 바인딩과 Origin 검사는 운영 인증·인가가 아니다. 이 프로토타입은 사용자 인증, 문서별 권한, 다중 사용자 운영을 제공하지 않는다.

자동 검증은 프로젝트 루트에서 각각 실행한다. 테스트는 합성 데이터와 격리된 임시 저장소를 사용하도록 작성돼 있다. 의존성이 없다면 백엔드 테스트용 `requirements-dev.txt`를 설치해야 한다.

```bash
cd frontend
npm test
npm run build
```

```bash
cd backend
source .venv/bin/activate
pip install -r requirements-dev.txt
python -m pytest -q
```

프론트 빌드의 번들 500kB 초과 안내는 React Flow 포함 때문이다.

Node.js 25는 내장 `localStorage`를 전역에 두어 jsdom의 것을 가린다. `frontend/vite.config.ts`가 테스트 작업자에 `--no-experimental-webstorage`를 넘기므로(그 플래그를 아는 Node에서만) 따로 설정할 것은 없다. 프론트 테스트가 `localStorage.clear is not a function`으로 무더기로 실패하면 이 설정이 빠졌는지 본다.

### 자주 보는 증상

| 증상 | 먼저 확인할 것 |
|---|---|
| 화면이 열리지 않음 | 5173 포트와 Vite 상태, 프론트 빌드 오류. 실제/Mock 데이터 로딩 실패를 화면 전체 오류와 혼동하지 않는다. |
| 실제 문서 목록/API가 실패 | 8000 포트, `/api/health`, Vite 프록시, 서버 콘솔. 원본 파일이나 SQLite를 지우기 전에 저장 경로와 실행 중 작업부터 확인한다. |
| Docling 처리 실패 | Docling 선택 의존성, PDF용 로컬 모델 경로, 파일 상태와 백엔드 오류. 모델을 임의로 외부에서 내려받았다고 가정하지 않는다. |
| PDF 완료 후 내용 일부가 빠짐 | 해당 실행의 OCR 설정과 빈 페이지 경고를 확인한다. 모델 위치는 README의 OCR 설정을 따른다. |
| 처리 결과가 이전 내용으로 보임 | 문서 상태와 `is_stale`을 확인한다. 재처리 중·실패 후 마지막 성공 결과가 의도적으로 남는다. |
| 처리 요청이 503 | 대기열 포화 또는 워커 미사용 상태다. 오류·이력을 확인하고 나중에 다시 요청한다. API 요청을 무한 반복하지 않는다. |
| 새 형식이 미지원 | Mock 파이프라인에 형식 카드가 있어도 실제 어댑터가 있는 것은 아니다. 실제 라우팅은 `backend/app/adapters/registry.py`를 확인한다. |

## 6. 다음에 이어갈 후보와 미결정 사항

다음 항목은 **추천 순서이지 사용자가 확정한 변경 지시가 아니다.** 다음 요청을 먼저 따르고, 독립적으로 할 수 있는 준비와 검증을 진행한다.

1. **파서 성능 측정**: 형식별로 본문·표·숫자·원문 위치가 얼마나 맞는지 재는 틀을 합성 샘플로 먼저 만든다(골드셋 버전 관리 기능은 만들지 않기로 했다). 구조 분석 결과(하위 문서·이미지 포함·암호화)를 측정 대상 선정에 쓴다.
2. 여러 파일을 업로드하는 동안 작업 탭을 벗어났을 때의 지속·취소·부분 성공·재개 동작을 먼저 명확히 하고 검증한다. 현재는 일부만 전송될 수 있다.
3. 실제 파일 처리 상태를 대시보드에 연결할 범위와 Mock/실제 전환 방식을 화면을 보면서 구체화한다. 지금은 두 데이터가 분리돼 있다.
4. 대표 합성 PDF·오피스·스캔 파일로 파싱 품질을 평가한다. OCR 후보 및 kordoc은 도입 전 한국어·영문, 표·문서번호·숫자·단위와 속도/자원/오류를 비교한다. 실제 고객 샘플 사용과 보관은 허용된 범위에서만 한다.
5. 구조 분석으로 찾은 링크·문서번호 후보를 업로드된 다른 문서와 실제로 맞춰 보는 연결 확인(대상 발견·미발견·후보 여러 개)과 순환 탐지. 현재 관계도 화면은 Mock이다.
6. 결과 부재와 저장 손상 등에 안정적인 오류 코드를 도입해 텍스트에 의존하는 프론트 분기를 줄인다. 기존 클라이언트와 테스트의 호환성을 같이 정한다.
7. 구조 분석의 형식 판별 결과를 파서 경로 선택에 연결하고(지금은 확장자 기준), 변경·삭제 추적을 설계한다. 파일 확장자 종류가 늘어날 수 있다는 전제를 유지한다.
8. 분류가 필요해지면 LLM 분류가 아니라 판단 결과만 돌려주는 System 1 형 모델을 우선 검토한다. 대상 환경 게이트웨이의 API·인증·허용 자원과 그 모델의 접속·성능을 확인한 뒤 어댑터를 정한다. API 키는 프론트·코드·문서에 넣지 않는다.
9. 실제 운영 범위가 정해지면 권한·비밀 관리, 보존/삭제, 내구성 대기열, 관측성, 인프라·배포 및 검색 연계를 별도로 설계한다. 현재 로컬 프로토타입이 이를 충족한다고 가정하지 않는다.

고객 원천별 파일 분포, 파싱 정확도 기준, 실제 검색·에이전트 계약, 원문 권한·버전 전달, 게이트웨이 반입 가능 모델, 스캔 비율과 인프라 한도는 아직 확인되지 않았다. 이 때문에 구현을 무조건 멈추기보다, 가상의 사례·교체 가능한 경계·명시적인 미확인 상태로 진행한다.
